# Контракт данных «План V3» (фаза 0 миграции)

Что лежит в файле экспорта, что с этим делает импорт и о какие места споткнётся
перенос в Postgres. Выведено из кода `План.html` (функции `_buildFullExportData`
и `_applyFullImport`), проверено тестом `tests/test_export_roundtrip.js`.

Версия документа: 31.07.2026. Обновлять при изменении формата экспорта.

---

## 1. Формат файла

Экспорт (меню «Файл» → скачивается `production_plan_ГГГГ-ММ-ДД.json`) — это плоский
объект с 21 ключом. Формата версии в файле **нет**: определять его приходится по
наличию полей (см. §3).

| Ключ | Тип | Содержание |
|---|---|---|
| `bases` | массив | Справочник баз |
| `nomenclature` | массив | Карточки изделий. Инвариант: одна карточка = один `articleGp`. Внутри `route[]` и `routeOverrides[]` |
| `ops` | массив | ОП и цеха. **Идентифицируются по `name`** — суррогатного ключа нет |
| `contracts` | массив | Контракты |
| `customerOrders` | массив | Заказы клиентов |
| `orders` | массив | Заказы на производство. ОП по переделам в `opRc`/`opAc`/`opSh`/`opU` — **массивы имён ОП** |
| `orderLinks` | массив | Связи заказ клиента ↔ заказ производства (`customerOrderId`, `productionOrderId`, `qty`) |
| `macroplan` | массив | Строки макроплана. **Не агрегируются**: каждая введённая запись — отдельная строка |
| `microplan` | массив | Строки по дням. Внутри `subOrders[]`, `launches[]`, работники |
| `schedules` | массив | Бригады и графики |
| `scheduleMonthOverrides` | массив | Помесячные правки графика |
| `calOverrides` | массив | Правки по дням, включая состав дня |
| `holidays` | массив | Праздники |
| `manualFrv` | массив | ФРВ по ОП и месяцам, внутри `frvSegments[]` |
| `manualFrvExtraMonths` | массив | Пустые столбцы-месяцы сводной ФРВ |
| `manualFrvPivotExtraRows` | массив | Доп. строки сводной ФРВ |
| `deliveryMatrix` | массив | Дни доставки между ОП |
| `planBaseline` | массив | Снимок изначального плана месяца |
| `macroEff` | массив | Эффективность (ОП, цех, месяц) для загрузки макроплана, % |
| `tcRcOverrides` | объект | `{ номер_заказа: норма_РЦ }` |
| `tcShOverrides` | объект | `{ номер_заказа: норма_ШЦ }` |
| `nextId` | число | Счётчик идентификаторов; при импорте **пересчитывается** (`recalcNextId`) |

**Ключи-словари.** `tcRcOverrides` и `tcShOverrides` — не массивы, а объекты с
номером заказа в качестве ключа. В реляционной схеме это таблица
`(order_number, stage, time_cost_min)`; номер заказа — строка, сравнение идёт
через `releaseOrderEq` (нормализует написание), это надо воспроизвести.

## 2. Импорт — это не «загрузить как есть»

`_applyFullImport` не просто раскладывает ключи по коллекциям: после присваивания
он прогоняет **22 функции миграции**, которые приводят исторические форматы к
текущему. Это отдельный слой, и его нельзя игнорировать при переносе в Django.

Порядок: присвоение коллекций → `migrate*` → `recalcAllMicroPlans()` →
`recalcNextId()` → `save()`.

Что делают миграции (сгруппировано):

- **Номенклатура:** `migrateNomenclatureToRoute` (плоские поля → `route[]`),
  `migrateNomenclatureRouteOverrides` (гарантирует массив `routeOverrides`),
  `migrateNomenclatureBundleRows`, `migrateNomenclatureProcessCosts`,
  `migrateNomenclatureAssortment`, `migrateNomenclatureBPBTK`.
- **Микроплан:** `migrateMicroplanArticleItems`, `migrateMicroplanWorkers`
  (старые `staffCount`/`attendance`/`shiftTime`/`effPct` → `workers[]`),
  `migrateMicroplanOrder2`, `migrateMicroplanStage`, `migrateMicroplanArticleByStage`.
- **Заказы:** `migrateOrderDeliveries`, `migrateOrderStageOps` (строка → массив ОП),
  `migrateOrderLinks` (строит связи из `order.contractId`, если их нет в файле).
- **Макроплан:** `migrateMacroplanProcessQty`, `migrateMacroplanVolumeType`.
- **Графики и ОП:** `migrateSchedulesGraphPreset`, `migrateScheduleWorkers`,
  `migrateOpsProcesses`, `migrateOpsBasesToBases` (базы выделены из ОП).
- **Контракты:** `migrateContractsQty`, `migrateContractsDeadlines`.

**Вывод для фазы 1.** Импортёр в Django обязан либо повторить этот слой, либо
принимать только уже нормализованные файлы. Практичный путь: прогонять файл через
браузерную версию (импорт → экспорт), получая нормализованный JSON, и только его
подавать на вход `import_json`. Тогда паритет проверяется на одном формате.

## 3. Ловушки, о которые споткнётся перенос

**Нет версии формата.** Определять приходится по признакам. Пример из кода: если
в файле нет `customerOrders`, но есть `contracts` — это старый формат, где контракты
и заказы клиентов были одной сущностью, и `_applyFullImport` расщепляет их на две.

**ОП идентифицируются по имени.** Переименование ОП рвёт ссылки во всех коллекциях
(микроплан, макроплан, графики, матрица доставок). В реляционной схеме нужен
суррогатный `id` плюс уникальное `name` и маппинг при миграции.

**У заказа нет единого поля `op`.** Есть четыре массива по переделам. Часть расчётов
по заказу поэтому идёт по базовому маршруту, а не по маршруту конкретного ОП — это
известное ограничение, воспроизводить как есть (CLAUDE.md §4.1).

**`nextId` не переносится.** При импорте пересчитывается по максимуму существующих
идентификаторов. В Postgres заменяется на sequence.

**Связи ЗК↔ПЗ восстановимы только частично.** Для файлов, где `orderLinks` нет,
`migrateOrderLinks` строит связь один-к-одному из `order.contractId`. Реальная связь
многие-ко-многим из таких файлов не восстановится — это потеря, а не ошибка переноса.

## 4. Исправлено 31.07.2026 (было потерей данных)

При обмене файлами между компьютерами — штатный сценарий работы — две коллекции
не попадали в экспорт и не сбрасывались при импорте:

- **`orderLinks`** (связи заказ клиента ↔ заказ производства);
- **`macroEff`** (эффективность ОП/цех/месяц в загрузке макроплана).

Обе редактируются в интерфейсе и сохраняются в localStorage, но в файл не писались.
Следствия было два, и второе хуже первого: при переносе данные терялись, а на
принимающей стороне в состоянии **оставались значения от предыдущего набора** —
`_applyFullImport` эти поля не трогал, а `migrateOrderLinks` при уже существующем
массиве выходит сразу. То есть связи от чужого набора указывали на несуществующие
заказы.

Сейчас обе коллекции есть в `_buildFullExportData` и явно выставляются в
`_applyFullImport`: `orderLinks` — в `null` при отсутствии в файле (тогда миграция
восстановит из `contractId`), `macroEff` — в пустой массив (восстанавливать нечем,
эффективность вернётся к дефолтным 100%).

Регрессия закрыта тестом `tests/test_export_roundtrip.js`: состав экспорта, импорт
чужого файла поверх текущих данных, обратная совместимость со старым форматом и
полный круг экспорт → импорт → экспорт.

## 5. Поля коллекций (снято с реального экспорта 01.08.2026)

Фикстура: `tests/fixtures/real_export_20260801.json` — 11 карточек номенклатуры,
6 ОП, 53 заказа, 48 строк макроплана, 315 строк микроплана, 22 бригады.
Поля ниже — фактические; то, что встречается не у всех записей, помечено.

**`nomenclature`** — `id`, `articleGp`, `articleItem`, `name`, `model`,
`assortmentGroup`, `normType` (`БП`/`БТК`), `nomOps[]`, `nomWorkshops[]`,
`route[]` (элементы: `stage`, `articleItem`, `name`, `timeCost`), `routeOverrides[]`,
`acFlag`, плюс легаси-нормы `timeCost`, `timeCostCut`, `timeCostPack`, `timeCostAc`,
`timeCostNorm` (в реальных данных нули — нормы живут в `route[].timeCost`).

**`ops`** — `id`, `name`, `workshop`, `type` (`БП`/`БТК`), `processType`
(`РЦ`/`АЦ`/`ШЦ`/`У`), `shiftDuration` (мин, дефолт 480), `frvMin`.

**`orders`** — `id`, `number`, `articleGp`, `name`, `quantity`, `contractNum`,
`opRc[]`/`opAc[]`/`opSh[]`/`opU[]` (массивы имён ОП), `deliveries[]` (`id`, `base`,
`date`, `quantity`), `deliveryDate` (не у всех), `contractId` (не у всех — связь
дублируется в `orderLinks`).

**`macroplan`** — `id`, `contractId`, `articleItem`, `op`, `workshop`, `month`
(`ГГГГ-ММ`), `qtySew`, `qtyRc`, `qtyAc`, `qtyPack`, `volumeType` (`main`/`extra`),
`eff`, `normOverride`, `orderNums[]` (не у всех — **без него норма из макроплана не
доходит до микроплана**, см. CLAUDE.md §4.3), `macroReleaseOrder` (редко).

**`microplan`** — `id`, `date`, `scheduleId`, `op`, `workshop`, `stage`,
`releaseOrder`, `articleItem`, `articleItems[]`, `planRelease`, `planLaunch`,
`factRelease`, `planReleaseMain`, `planReleaseExtra` (всегда 0 — механику убрали),
`planByArticle` (объект артикул→штуки), `planReleaseIsManual`, `workers[]`,
`subOrders[]`, `launches[]`, `learningEff` (не у всех, дефолт 100),
`contractId` (не у всех), `comment` (редко).

## 6. Что покрывают реальные данные, а что нет

Проверено по фикстуре. Важно для планирования golden-набора: **непокрытое
означает, что Python-порт по этим веткам сверить будет не с чем.**

| Кейс из ТЗ | В данных |
|---|---|
| Норма РЦ по заказу (`tcRcOverrides`) | есть, 6 заказов |
| Норма из макроплана с привязкой заказов | есть, 27 строк |
| Подзаказы (2-й заказ в смене) | есть, 117 в 73 строках |
| Перевыполнение (факт > план) | есть, 62 строки |
| Недовыполнение (0 < факт < план) | есть, 33 строки |
| Три передела РЦ / ШЦ / У | есть (63 / 189 / 63) |
| Ручной план | есть, 65 строк |
| **Route overrides (разные маршруты по ОП)** | **нет** |
| **Норма ШЦ по заказу (`tcShOverrides`)** | **нет** |
| **Эффективность освоения ≠ 100%** | **нет** |
| **Заказ на нескольких ОП по одному переделу** | **нет** |
| **Запуски (`launches`)** | **нет** |
| **«Доп. объём» (`__extra__`)** | **нет** |
| **Передел АЦ** | **нет** (в данных только РЦ/ШЦ/У) |

Первые семь строк — то, ради чего golden-набор и нужен: обе проблемные ситуации
(опережение и отставание) представлены в боевых данных десятками строк.
Непокрытые ветки закрываются либо вторым экспортом с другой фабрики, либо
синтетическими фикстурами (частично уже есть в `test_order_remainder.js`).

## 7. Эталон расчётов (golden-master)

`tests/fixtures/golden/` — эталонные выходы, снятые с фикстуры скриптом
`golden_snapshot.js`:

- `microplan.json` — план и факт по всем 315 строкам, включая подзаказы;
- `order_coverage.json` — покрытие по 33 парам заказ+передел (метрика `orderCoveredBefore`);
- `norms.json` — норма для каждой пары заказ+передел+артикул.

Сверяет с ними `tests/test_golden_real.js`. Он же проверяет **идемпотентность**:
повторный `recalcAllMicroPlans()` не должен двигать план.

**Ключевой факт для фазы 2:** на реальных данных пересчёт совпал с сохранённым
планом на всех 315 строках из 315. То есть ядро детерминировано и воспроизводимо —
Python-порту есть с чем сверяться построчно, а не «примерно».

Пересnимать эталон (`node golden_snapshot.js`) — только осознанно, после проверенной
правки расчётов, и с обязательным просмотром, что именно изменилось.
