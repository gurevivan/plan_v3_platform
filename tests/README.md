# Тесты расчётного ядра «План V3»

Проверяют доменную логику `План.html` в Node, без браузера. Это заготовка
golden-master набора из фазы 0 плана миграции на Django: те же кейсы позже станут
эталоном для Python-порта.

## Как запускать

```bash
cd tests
./run.sh                                        # текущий План.html
./run.sh ../backups/План_20260731_190001.html   # любая копия из backups/
```

`run.sh` собирает харнесс, проверяет синтаксис и прогоняет все `test_*.js`.
Код возврата 0 — всё зелёное; 1 — есть падения.

## Как устроено

| Файл | Назначение |
|---|---|
| `build.py` | извлекает `<script>` из HTML, вырезает IIFE `populateModules()`, добавляет экспорт в `__T` → `_build/harness.js` |
| `sandbox.js` | поднимает харнесс в `vm` с заглушками DOM/localStorage; глушит `save()`/`renderActive()` |
| `test_*.js` | сами проверки |
| `_build/` | генерируемое, в репозиторий не нужно |

IIFE `populateModules()` вырезается намеренно: она ссылается на неопределённые
функции, в браузере это тихая ошибка в самом конце (приложение уже работает),
а в Node роняет загрузку. См. CLAUDE.md §6 и §8.

## Что покрыто

**`test_order_remainder.js` — единая метрика покрытия заказа.**
Регрессия на баг «план 0 при живом остатке ≤N (ЗАК)» (`BUG_план0_при_остатке_ЗАК.md`).
Правило: прошлое считаем по факту, будущее — по плану; подсказка и ядро авто-плана
обязаны давать одно число. Кейсы: перевыполнение, недовыполнение, отсутствие факта,
подзаказы в покрытии, закрытый по факту заказ, разделение переделов.

**`test_row_order_change.js` — смена заказа в строке микроплана.**
При исправлении заказа пересчитываются изделие и норма; если артикул подходит и
новому заказу (тот же ГП), выбор пользователя сохраняется.

## Как добавить проверку

```js
const { load, makeChecker } = require('./sandbox');
const ctx = load();          // ctx — это globalThis приложения
const T = ctx.__T;           // T.S — состояние, доступно на чтение и запись
const { check, finish } = makeChecker();

T.S = Object.assign({}, T.S, { /* минимальное состояние под кейс */ });
check('что проверяем', ctx.someFunction(...), ожидаемое);
finish();
```

Если нужной функции нет в `__T`, её можно взять прямо из контекста (`ctx.имяФункции`) —
все функции приложения глобальные.

## Golden-master на реальных данных

`fixtures/real_export_20260801.json` — боевой экспорт (315 строк микроплана,
53 заказа, 22 бригады). `fixtures/golden/` — эталонные выходы, снятые с него.

```bash
node golden_snapshot.js          # пересnять эталон (осознанно!)
node golden_snapshot.js другой_экспорт.json
```

`test_golden_real.js` сверяет с эталоном план по строкам и подзаказам, покрытие
заказов, нормы, и проверяет идемпотентность пересчёта. Тест пропускается
(`SKIP`), если фикстуры нет — так набор остаётся рабочим на машине без боевых данных.

**Эталон пересnимают только после проверенной правки расчётов**, посмотрев
глазами, что именно изменилось. Иначе тест начнёт «подтверждать» регрессию.

Что реальные данные покрывают, а что нет — таблица в `DATA_CONTRACT.md` §6.
Коротко: перевыполнение, недовыполнение, подзаказы и нормы РЦ есть; маршруты на
уровень ОП, норму ШЦ по заказу, эффективность освоения ≠ 100%, запуски и передел АЦ
покрыть нечем — для них нужны либо второй экспорт, либо синтетические фикстуры.

## Серверный режим

| файл | что проверяет | нужен сервер |
|---|---|---|
| `test_server_mode.js` | справочники: перехват обработчиков вкладки, конфликт версий, переводы формата | нет, сеть подменена |
| `test_server_sync.js` | синхронизация вкладок планирования по разнице: что она НЕ делает | нет, сеть подменена |
| `test_server_roles.js` | роли: чужой раздел не отправляется, а правка убирается с экрана | нет, сеть подменена |
| `test_server_audit.js` | журнал изменений: сущности вкладки, читаемый вид, история не оседает в `S` | нет, сеть подменена |
| `test_server_boot.js` | что показывается при открытии страницы: в серверном режиме локальный снимок не выводится | нет |
| `live_api_check.js` | всё состояние туда и обратно через настоящий API, сверка с боевой выгрузкой | да |

В `test_server_roles.js` главное — не «отказ показан», а что после отказа правка
**убрана с экрана**. Показанная, но не сохранённая строка хуже прямого отказа:
человек уходит с уверенностью, что план записан. Настоящий запрет живёт на
сервере (`server/core/api/test_api.py`), клиент лишь не даёт заполнять форму,
которая всё равно не сохранится.

Живая проверка — единственная, которая ловит поле, которое интерфейс читает, но
не отправляет обратно. Тест с подменённой сетью такую потерю подтвердит как
«работает»: он видит только то, что клиент отправил, и не знает, чего он не
отправил. Так были найдены `planReleaseMain` подзаказов и не уходившие на сервер
маршруты номенклатуры.

```bash
tests/live_reset.sh                        # залить фикстуру и поднять сервер на 8011
cd tests && OUT_DIR=/tmp node live_api_check.js
cd server && ../server_venv/bin/python manage.py compare_json \
    ../tests/fixtures/real_export_20260801.json /tmp/live_from_api.json
cd server && ../server_venv/bin/python manage.py compare_json \
    ../tests/fixtures/real_export_20260801.json /tmp/live_after_push.json
```

Обе сверки обязаны сказать «эквивалентен». Проверять саму проверку — подменами:
сломать одно место в `toSrv` и убедиться, что сверка это видит.
