# CLAUDE.md — «План V3» (планирование швейного производства)

Инструкция для Claude Code, работающего с этим проектом на сервере. Прочитай целиком
перед любыми правками. Здесь зафиксированы архитектура, доменные инварианты, способ

## 1. Что это за проект

`План.html` — **одностраничное веб-приложение** (~11 800 строк: HTML + CSS + ванильный
JS в одном `<script>`). Назначение: оперативное планирование швейного производства
(контракты → макроплан → заказы на производство → микроплан → график → аналитика).

**Это НЕ python-проект**, несмотря на путь `/home/ivan/Python/...`. Никакой сборки,
фреймворков, npm-зависимостей и (на машине пользователя) git нет.

## 2. Стек и жёсткие ограничения

- Чистый HTML/CSS/JS, всё в одном файле. **Не вводить сборщики, фреймворки, модули ES.**
- Состояние приложения — глобальный объект **`S`** (`let S = {…}`), хранится в
  **localStorage** под ключом `prod-plan-v6` и резервно в IndexedDB. Обмен между
  компьютерами — через экспорт/импорт JSON (меню «Файл»).
- Все функции — **глобальные** (объявлены `function …` на верхнем уровне), потому что
  навешаны на инлайновые `onclick`/`onblur`/`onchange` в генерируемом HTML. Внутри есть
  IIFE `populateModules()` с неймспейсами Store/Utils/Validation/Views/Events, но
  обработчики ходят в глобальные имена. **Не превращай функции в локальные/стрелочные
  на верхнем уровне — сломаются инлайн-хендлеры.**
- Рендер вкладок — через `innerHTML` (`renderActive()` → `renderTab(tab)` →
  `renderContracts/renderMacroplan/renderProductionOrders/renderMicroplan/renderSchedules/
  renderAnalytics/renderRefs/...`). После правок данных вызывают `save()` и `renderActive()`.

## 3. Доменная модель

Стадии (переделы) производства, физический поток **ВСЕГДА**: `РЦ → АЦ → ШЦ → У → База`
(Раскройный цех → Цех автоматизации → Швейный цех → Упаковка → База). АЦ может
отсутствовать в маршруте.

Главные коллекции в `S`:
- `S.nomenclature` — карточки изделий. **Инвариант: одна карточка = один `articleGp`**
  (на это опираются ~30 лукапов `S.nomenclature.find(x => x.articleGp === gp)`).
  Внутри `n.route = [{stage, articleItem, name, timeCost}]` + `n.routeOverrides`.
- `S.ops` — ОП/цеха: `{name, workshop, processType: 'РЦ'|'АЦ'|'ШЦ'|'У', …}`.
  **ОП идентифицируются по `name`.**
- `S.contracts`, `S.customerOrders` — контракты и заказы клиентов.
- `S.orders` — заказы на производство. **У них НЕТ поля `op`** (op есть только у строк
  макро/микроплана). Один заказ может делаться на нескольких ОП на один передел
  (поля `opRc`/`opAc`/`opSh`/`opU` — массивы имён ОП).
- `S.macroplan` — строки макроплана `{contractId, articleItem, op, workshop, month,
  qtySew, eff, normOverride?, orderNums?, volumeType:'main'|'extra'}`.
- `S.microplan` — строки микроплана `{date, op, workshop, stage, scheduleId, articleItems,
  planRelease, factRelease, planReleaseIsManual, learningEff, subOrders[], launchEntries[]}`.
- `S.schedules` — бригады/графики `{id, name, op, workshop, …, activeMonths}`.
- `S.tcRcOverrides`, `S.tcShOverrides` — `{ номер_заказа: норма }` для РЦ и ШЦ (см. §4.3).
- `S.planBaseline` — снимок изначального плана месяца (план на 100%, фиксируется при первом
  вводе факта в месяце) — для секции аналитики «План (изначальный) ↔ Факт».

## 4. Ключевые архитектурные решения (НЕ ломать)

### 4.1 Маршрут на уровень ОП (route overrides)
Разные ОП могут иметь разные маршруты для одного `articleGp` (ОП-5 шьёт костюм целиком
`01.000001`, остальные — куртка/брюки/рубашка `/1,/2,/3`), **без дублирования карточек**.
- `n.route` — базовый; `n.routeOverrides = [{op, route:[…]}]` — переопределения.
- Резолверы: `routeForOp(n, op)` (override если непустой, иначе базовый; `op` falsy →
  базовый), `allRoutesOf(n)` (объединение всех маршрутов), `migrateNomenclatureRouteOverrides()`.
- Свойство безопасности: пока `routeOverrides` пуст — `routeForOp === n.route`.
- Известное ограничение: функции, берущие только `articleGp` без op (т.к. `S.orders`
  не несут op — напр. `factByOrderStageKits`), используют базовый маршрут; для ОП с
  override комплектная проверка может быть неточной. Семейство
  `stageFactLimit/validateStageFact/validateStageLaunch` уже принимает op.

### 4.2 Норма (трудоёмкость) — по ПЕРЕДЕЛУ строки, не по первому совпадению
Один `articleItem` может встречаться на нескольких переделах (костюм и в ШЦ, и в У).
Норму всегда берут по стадии строки: `stageTimeCostFor(ai, stage, op)`, `tcForMicroRow`,
`macroRowLaborMinutes`. Цех упаковки (У) обязан брать норму У, а не ШЦ.

### 4.3 Норма РЦ — индивидуальная по заказу
Для РЦ у **каждого заказа** может быть своя норма. Хранится в `S.tcRcOverrides[номер_заказа]`
и/или в строке макроплана с привязанным заказом (`normOverride` + `orderNums`).
Приоритет нормы в `tcForMicroRow` (и в `tcForSubOrder`):
1. `normFromMacroForOrder(order, ai, stage)` — норма из строки макроплана, где
   `orderNums.includes(order)`;
2. РЦ-override `S.tcRcOverrides[order]` (только stage РЦ);
3. `stageTimeCostFor(ai, stage, op)` → иначе `timeCostOf(ai, op)`.
**Поэтому норма РЦ доходит до микроплана только если у строки макроплана привязан заказ.**

### 4.4 Авто-план микроплана = пул мощности бригады-дня
- Группа бригады-дня (`brigadeDayGroupRows`) = строки с одним `scheduleId` (или
  `op|workshop`) + дата + передел.
- Сырой физический пул (`brigadeDayPoolRawMin`) = Σ `workersAvailableMinSum`
  (= ФРВ × 0.95 (абсентеизм) × эфф. работников), БЕЗ эфф. освоения.
- Каждая строка/подзаказ потребляет физ.минуты = `штуки × норма / эфф.освоения`;
  остаток пула делят авто-строки (`brigadeDayUsedByOthersRawMin`).
- `_recalcPlanReleaseCore(row)` — ядро одной строки; `recalcAllMicroPlans()` сбрасывает
  авто-планы и считает СНАЧАЛА ручные (`planReleaseIsManual`), потом авто.
- `learningEff` («Эфф. освоения», max 200%) — линейный множитель выработки; >100%
  раздувает план сверх физической мощности (известная семантика, не баг).

### 4.5 Подзаказы (subOrders) и остаток заказа
«Второй заказ в смене» = подзаказ (`row.subOrders[]`), производит тот же передел/дату,
что родительская строка. **Инвариант:** любой подсчёт «сколько запланировано/выпущено по
заказу+переделу» ОБЯЗАН включать и main-строки, и `subOrders[]` других строк — иначе
остаток (`≤N (ЗАК)`) и авто-план переполняются. Единый хелпер:
`orderStagePlannedQty(orderNum, stage, baseDate, {excludeRowId, metric, when, skipManualMain, articleItem})`.
`excludeRowId` исключает строку целиком (main + её подзаказы) — вклад своей строки
вызывающий добавляет явно. Трудоёмкость подзаказа — `tcForSubOrder(sub, op, stage)`
(тот же приоритет норм, что в §4.3), НЕ `calcTcForArticleItems2`.

### 4.6 Режимы проверок микроплана: «Без / Прямой / От ШЦ» (`microCheckMode`)
- `microValidation` = производное (`mode !== 'off'`).
- **«От ШЦ» — это НЕ разворот цепочки.** Поток физически всё равно РЦ→АЦ→ШЦ→У. Смысл:
  ШЦ — самый трудоёмкий, его планируют первым как якорь. `prevStageInRoute` возвращает
  `null` для ШЦ → к ШЦ не применяются upstream-проверки. На строке ШЦ — инфо-индикатор
  готовности кроя (have/need), план ШЦ при этом не блокируется.
- **Грубая ошибка, которую нельзя повторять:** разворачивать `prevStageInRoute`/порядок
  стадий в ШЦ→АЦ→РЦ→У (даёт бред «шьём до кроя», «доставка с ШЦ на раскрой»).

### 4.7 Единая метрика покрытия заказа — `orderCoveredBefore` (31.07.2026)
**Правило: ПРОШЛОЕ СЧИТАЕМ ПО ФАКТУ, БУДУЩЕЕ — ПО ПЛАНУ.** Граница проходит там, где в
смену введён факт (метрика `factOrPlan` в `orderStagePlannedQty`).

- `orderCoveredBefore(orderNum, stage, baseDate, opts)` — единственная точка ответа на
  вопрос «сколько по заказу+переделу уже покрыто ДО этой даты» (с подзаказами, §4.5).
- «Остаток к планированию» = кол-во заказа − покрыто ранее − запланировано в ту же дату.
- Через хелпер ходят ВСЕ 7 потребителей: подсказка `≤N (ЗАК)` (`validatePlanOrderLimit`),
  три ветки ядра `_recalcPlanReleaseCore` (главный заказ при подзаказах / один артикул /
  несколько артикулов), лимит подзаказа в ядре, подсказка лимита подзаказа в рендере,
  признак «заказ закрыт» в `compressPlanFromFactCore`.
- **Метрику остатка менять только внутри `orderCoveredBefore`.** Раньше её задавали в
  каждом месте отдельно и они разошлись: подсказка считала по `plan`, ядро по `maxFactPlan`.
  При перевыполнении ядро считало заказ выбранным и ставило план 0, а подсказка показывала
  живой остаток (баг «план 0 при остатке 618»). При недовыполнении `maxFactPlan` засчитывал
  невыполненный план как сделанный, и хвост заказа молча исчезал вместо удлинения графика.
- Регрессия закрыта тестом `tests/test_order_remainder.js` (см. §6).
- Это **не** возврат перепланировщика: авто-план по-прежнему не двигает строки от факта,
  меняется только то, как считается остаток. `compressPlanFromFact` остаётся ручной кнопкой
  с подтверждением.

### 4.8 Два уровня проверок микроплана — `severity` (31.07.2026)
Каждая `validate*` при неуспехе возвращает `severity`:
- **`'stop'`** — физическое нарушение или порча данных: нельзя сшить больше, чем накроено;
  выпуск больше суммы запусков; факт больше количества заказа. Почти всегда опечатка →
  ввод блокируется модальным «Всё равно сохранить?». Это `validateStageFact`,
  `validateFactVsOrderQty`, `validateStageLaunch`, `validateReleaseVsLaunches`.
- **`'warn'`** — расхождение планирования: план разошёлся с остатком заказа
  (`validatePlanOrderLimit`) или с планом предыдущего передела (`validatePlanVsPrevStagePlan`).
  Нормальная жизнь цеха (идём с опережением или отстаём), а НЕ ошибка ввода →
  **не блокируем**: сохраняем и показываем жёлтый индикатор в строке (лимит, превышение
  `⚠ +N`, полный текст в title) + янтарная полоса слева у ячейки плана (`_planWarn`).

**Правило: проверки ФАКТА — stop, проверки ПЛАНА — warn.** Раньше все били модалкой, и при
любом отклонении от макроплана заполнение микроплана превращалось в череду подтверждений.
`setMicroPlanManual` больше не вызывает `_confirm`; `updMFact` и обработчики запусков — вызывают.
Регрессия закрыта тестом `tests/test_validation_severity.js`.

## 4а. Серверная версия — где что лежит (фаза 1, 01.08.2026)

Каталог `server/` — Django + DRF + Postgres. **Пока только слой данных**: схема,
импорт JSON-экспорта в базу, выгрузка обратно. Расчётного ядра там ещё нет.

- Виртуальное окружение: `server_venv/` (`../server_venv/bin/python manage.py …`).
- База: контейнер `plan-pg`, Postgres 16, порт **5433** (не 5432 — чтобы не
  столкнуться с чужим), volume `plan_pgdata`, лимит памяти 384 МБ.
- Команды: `import_json`, `export_json`, `compare_json`. Инструкция — `server/README.md`.
- Критерий приёмки фазы 1 выполнен: круговой рейс JSON → БД → JSON эквивалентен
  исходнику на боевых данных, и после базы расчёты дают тот же план, что эталон.

**API (фаза 3, в работе)** — `server/core/api/`. CRUD плюс `microplan/recalc`,
`microplan/validate`, `analytics`, `export`. Инструкция — `server/README.md`.

- **Ограничение по ОП — в QuerySet И в срезе для расчётов.** Фильтровать только
  вывод недостаточно: расчёт всё равно видел бы чужие площадки. Отсутствие записей
  `UserOpAccess` = доступ ко всем ОП (для администратора).
- **Пересчёт по умолчанию НЕ пишет в базу** — возвращает результат; запись только
  при `commit: true` и только по ОП с правом правки.
- **Срез собирается через `build_export()`** — тот же формат, на котором ядро сверено
  с оригиналом. Второй способ подать данные в расчёт не заводить.
- Тесты: `pytest core/api/test_api.py`. Проверяют свойства (чужое не видно, версия
  конфликтует, без commit база не меняется), а не коды ответов.

**Роли (02.08.2026)** — `server/core/api/roles.py`. Два независимых измерения:
раздел («что правит») и площадка («где»). Право на запись — их пересечение.

- **Один факт — одно место.** Человек и пароль — в `auth_user`; роли — в группах
  Django (`auth_group`); площадки — в `UserOpAccess`; связь «раздел → адреса API» —
  в коде. Своей таблицы пользователей или ролей НЕТ и заводить нельзя: второй
  экземпляр того же факта однажды разойдётся с первым — ровно так в приложении
  разошлись экспорт и импорт и потеряли `orderLinks`.
- **Администратор — это `is_superuser`, и только он.** Роли «Администратор» нет
  намеренно. `IsSystemAdmin` (не штатный `IsAdminUser`, тот смотрит на `is_staff` —
  это доступ в админку Django, а не право раздавать права). `is_staff` выставляется
  следом за `is_superuser`, отдельно не спрашивается.
- Роли: `Справочники`, `Заказы`, `Макропланирование`, `Микропланирование`.
  Отсутствие ролей = «только смотрит»; отдельной роли под это нет — это тот же
  факт во второй раз.
- **Раздел viewset'а не задаётся руками** — выводится в `urls.py` из пути роутера
  по `SECTION_BY_PREFIX`. Новый путь без раздела роняет импорт: молча он оказался
  бы открыт всем на запись.
- **Ограничивается запись, не чтение.** Аналитика считается на клиенте по
  микроплану, макроплану, заказам и справочникам сразу — запрет читать раздел
  сломал бы её тому, кому её открыли. Чтение и так режется по ОП.
- Снять последнего активного администратора нельзя (`_guard_last_admin`): и
  снятием галочки «администратор», и деактивацией, и удалением.
- `/api/access` убран: доступы к ОП правятся только внутри `/api/users/{id}`.
  Два пути записи в одну таблицу — та же болезнь, что две карты полей.
- В интерфейсе: `srvCanEdit(section)` + барьер `srvGuardEdit` в `srvCreate/
  srvUpdate/srvDelete` и в `_srvSyncOnce`. **Отказ обязан откатывать экран**
  (перечитать раздел): иначе правка осталась бы видна, но не сохранена, и человек
  ушёл бы уверенным, что план записан. Клиентская проверка — только удобство;
  истина на сервере, поэтому при неизвестном пользователе или незагруженном
  каталоге правку НЕ запрещаем (сбойный `me` иначе парализовал бы смену).
- Экран управления людьми — `srvUsersDialog()`, кнопка в полосе режима у админа.
  Пользователи в `S` не кладутся: вторая версия прав разошлась бы с настоящей.
- Тесты: `pytest core/api/test_api.py` (45) и `tests/test_server_roles.js` (44).
  Проверены подменами — 8 серверных и 5 клиентских ловятся.

**Серверный режим в интерфейсе (фаза 4 ЗАКРЫТА, 02.08.2026)** — модуль `SRV` в
`План.html` перед IIFE `populateModules()`. Переведены ВСЕ видимые вкладки:
справочники, контракты, заказы на производство, ФРВ, макроплан, график,
микроплан, аналитика. Скрытые вкладки («Главная», «Заказы клиентов»,
`style="display:none"`) не переводились — их нет в интерфейсе.

- **Переключатель по умолчанию выключен** (`localStorage['plan-server-mode']`).
  Пока выключен — приложение работает из localStorage, как раньше. Включение
  тянет ВСЕ коллекции (`SRV_LOAD_ORDER`) и пересчитывает `nextId`: держать часть
  данных на сервере, а часть локально нельзя — расчёт ходит по всем коллекциям
  сразу и на смеси даст неверный план.
- `План.html` отдаётся Django (`core/api/pages.py`) — один адрес со страницей и API,
  иначе CORS и куки сессии.
- Правка отправляет `version`; на 409 список перечитывается, пользователю
  говорится прямо. Не затирать чужое молча.
- `SRV` объявлен через `const`, поэтому в харнесс он попадает отдельной строкой
  в `tests/build.py` — иначе тесты его не увидят.

**Одна копия данных (03.08.2026).** В серверном режиме `save()` НЕ пишет в
localStorage и IndexedDB — только `srvSync()`. Раньше состояние жило в двух
местах, и локальная копия становилась «тенью»: при следующем открытии
показывалась первой, а при недоступном сервере так и оставалась — с виду
рабочая. Почти все истории «данные пропали» выросли отсюда.

- При старте в серверном режиме локальный снимок на экран не попадает
  (`srvResetStateForServer`), данные приходят из базы.
- Прежнее содержимое localStorage НЕ трогаем: это состояние автономной работы.
  При выключении режима оно возвращается (`loadLS()` в `toggleServerMode`) —
  иначе первое же сохранение записало бы поверх него серверные данные.
- Настройки интерфейса (тема, вкладка, режим проверок) остаются в браузере: они
  у каждого свои и в базу не ходят.
- Плата: неотправленная правка живёт только в памяти. `srvHasUnsent()` +
  `beforeunload` спрашивают перед уходом со страницы. Раньше её подобрал бы
  localStorage, но на сервер она всё равно не попадала — потеря была та же,
  просто отложенная.

**Два механизма отправки — и это осознанно:**

1. **Справочники — точечный перехват.** `addOp`/`updOp`/`delOp` и им подобные при
   `SRV.on` сами ходят на сервер и НЕ трогают локальную копию. Новая сущность =
   строка в `SRV_ENTITIES` плюс `if (SRV.on)` в обработчики вкладки.
2. **Вкладки планирования — синхронизация по разнице** (`sync: true` в
   `SRV_ENTITIES`). Обработчики работают как раньше: правят `S` и зовут `save()`.
   `save()` — единственная точка отправки: `srvSync()` сравнивает коллекцию со
   СЛЕПКОМ (`SRV.mirror`) того, что сервер видел последним, и шлёт только разницу.
   Перехватывать там каждый обработчик нельзя: их больше полусотни
   (`updMacroCell`, `updMacroRowMonth`, `updMicroWorkerField`, …), и забытый
   обработчик молча правит только экран.

**Правила синхронизации, которые нельзя нарушать:**

- **Нет слепка — нет синхронизации.** `srvLoad` при ошибке зовёт `srvForget`.
  Иначе недогруженный список выглядел бы как «пользователь всё удалил», и
  синхронизация вычистила бы сервер. Массовое удаление (>5 записей и >20 % коллекции)
  дополнительно спрашивает подтверждение.
- **«Поля не было» ≠ «поле равно значению по умолчанию».** Сервер отдаёт колонки
  всегда, поэтому у пустой смены работника там лежит 480. В «Плане» пустая смена
  означает «как у ОП» (в цехе упаковки 720) — подставленные 480 срезали бы треть
  мощности. Поэтому API отдаёт `absent_fields`/`null_fields` (из `extra['__absent']`
  и `extra['__null']`), клиент выбрасывает эти поля и сообщает их обратно.
- **Несмоделированные поля не теряются.** Всё, чего нет в колонках, лежит в `extra`
  и ходит через `extra_fields`. Там живёт СОСТАВ РАБОТНИКОВ на конкретный день
  (`calOverrides[].workers`) и старые поля норм номенклатуры. Набор «своих» полей
  выводится из самого `toLocal` (`srvOwnKeys`), а не задаётся вторым списком.
- **Загрузка файла в серверном режиме запрещена** (`importAllData`): она замещает
  данные целиком и разошлась бы с базой. Состояние на сервер заливает администратор
  (`/api/import`).
- **Выгрузка чистится от `srvId`/`srvVersion`** (`_stripSrvKeys`), иначе они уехали
  бы в `extra` записи и вернулись в следующем экспорте.
- Аналитика считается на клиенте по данным сервера (ядро сверено эталонами,
  фаза 2), кнопка «Сверить с расчётом сервера» проверяет это вживую.

Причин две, и обе закрыты:

**Доступ по ОП — самая частая причина «данные пропали» (02.08.2026).** Записи
`UserOpAccess` режут не только планы, но и справочник ОП (`OpViewSet.op_field =
'name'`). Пользователь с доступом к площадке, которой нет в данных, видит: ops 0,
microplan 0, schedules 0, macroplan 0 — при этом номенклатура и контракты видны,
потому что к ОП не привязаны. Поэтому:

- полоса режима показывает площадки **по чтению** (`ops_read`), а не по правке:
  раньше человек с доступом к одной площадке не понимал, почему у него пусто;
- `srvUserSave` НЕ отправляет `ops`, когда справочник ОП в браузере пуст. Иначе
  «ни одной отмеченной» стёрло бы человеку все выданные площадки — молча и не тем
  действием, которое затевалось. Сервер при отсутствии ключа доступы не трогает;
- подпись «ни одной не отмечено = все площадки» стоит всегда: снимая последнюю
  галочку, администратор ОТКРЫВАЕТ всё, а не закрывает.

**Журнал изменений (02.08.2026)** — модель `ChangeLog`, `server/core/api/audit.py`,

- **Хранится РАЗНИЦА, а не копия записи** (`{поле: [было, стало]}`). Готовые
  решения вроде `django-simple-history` кладут снимок строки на каждое

- Пустую разницу не пишем: интерфейс шлёт запись целиком при каждом уходе из

и импорт разошлись именно так и потеряли `orderLinks` с `macroEff`.

**Расчётное ядро (фаза 2 ЗАКРЫТА)** — `server/core/calc/`: перенесены все восемь групп
(даты/доставки, маршруты, нормы, ФРВ/мощность, авто-план, покрытие заказа, семь
проверок, аналитика). Вёрстка аналитики осталась во фронте — переносилась расчётная
часть `renderAnalytics`, а не построение HTML.

- Паритет: `cd tests && node golden_calc.js` снимает эталоны с JS,
  `pytest core/calc/test_parity.py` сверяет. **Группа считается перенесённой
  только при зелёном эталоне.**
- `Snapshot` несёт индекс `(заказ, передел)` — из-за него покрытие заказа стало
  константным вместо линейного: 3,2 мкс против 634 мкс на 5040 строках.
- **Грабли переноса:** `stageOfMacroRow` определяет передел строки по паре
  (ОП, цех), и она ПРИОРИТЕТНЕЕ поля `row.stage`. Наивный порт `row.stage || 'ШЦ'`
  дал неверную норму на 24 строках боевых данных (1.05 вместо 1.35). Поймал
  эталон — без него уехало бы в авто-план.
- **Боевых данных мало для паритета.** В них каждая бригада-день = одна строка,
  эфф. освоения везде 100 %, смены только 480, цеха только БП. Деление пула между
  строками (`brigadeDayUsedByOthersRawMin`) на них не проверяется вовсе. Для таких
  веток заведена `tests/fixtures/synthetic_capacity.json` — сверка двух реализаций
  между собой, поэтому синтетика законна. **Проверяй эталон на пустоту**, прежде
  чем считать группу перенесённой.
- **Эталон обязан нести состояние, на котором посчитан** (`golden/…state.json`):
  импорт прогоняет миграции и пересчёт, и авто-строки уезжают от файла фикстуры.
- **Зелёные тесты проверяй подменами.** Пять подмен в авто-плане ловятся, но три
  из них — только благодаря синтетике. При таких проверках отключай кэш байт-кода
  (`PYTHONDONTWRITEBYTECODE=1`): подмена и откат укладываются в одну секунду при
  неизменном размере файла, Python берёт старый `.pyc` и даёт ложный вывод.
- **Комплектность в аналитике** (`kit_qty_from_entries`): штуки готовой продукции —
  НЕ сумма строк. Целые изделия складываются, узлы (`/1`, `/2`) сводятся по минимуму.
  И передел агрегации без фильтра — САМЫЙ ГЛУБОКИЙ с данными, не первый: складывать
  все переделы нельзя, у изделия «целиком» артикул ГП стоит и на ШЦ, и на У.
- **Комплектность упаковки** (`stageFactLimit` для У): лимит = МИНИМУМ по частям
  предыдущего передела, не сумма. Упаковать можно столько комплектов, сколько собрано
  самой дефицитной части. Ни в боевых данных, ни в первой синтетике изделий из
  нескольких частей не было — правило не проверялось вообще, пока не добавил ГП-03
  «Костюм» с курткой и брюками.
- **Тексты сообщений валидаций сверяются дословно** — их видит пользователь. На этом
  поймано, что в сообщении о запуске подставляется НАЗВАНИЕ изделия (`nameOf`), а не
  код артикула.
- **`Math.round` ≠ `round()`.** В JS половина округляется вверх, в Python —
  к чётному: `round(2.5)` даёт 2. В плане это расхождение на штуку. Порт использует
  `js_round`.
- **Две разные формулы множителя освоения в оригинале:** в ядре
  `max(0.01, x)/100`, в `brigadeDayUsedByOthersRawMin` — `max(0.01, x/100)`.
  Совпадают на всех достижимых значениях (1..200), расходятся на 0. Порт
  воспроизводит каждое место как есть; унификация — правка в JS, с пересъёмкой эталона.

## 6. Как проверять изменения (ОБЯЗАТЕЛЬНО)

**Тестового JSON «по умолчанию» нет, данные живут в localStorage браузера.** Поэтому:

1. **Синтаксис** после каждой правки:
   ```bash
   python3 -c "import re;open('/tmp/scr.js','w').write(re.findall(r'<script>(.*?)</script>',open('План.html',encoding='utf-8').read(),re.S)[0])" && node --check /tmp/scr.js && echo OK
   ```
2. **Логика расчётов — каталог `tests/` (готовый харнесс, собирать заново не нужно):**
   ```bash
   cd tests && ./run.sh                                       # текущий План.html
   cd tests && ./run.sh ../backups/План_20260731_190001.html  # любая копия для сравнения
   ```
   `run.sh` собирает харнесс (`build.py`: вырезает IIFE `populateModules()`, добавляет
   экспорт в `__T`), проверяет синтаксис и прогоняет все `test_*.js`. Код возврата 0 —
   зелено. Подробности и как добавить проверку — `tests/README.md`.
   **После правки расчётов прогонять обязательно**, и полезно прогнать те же тесты против
   бэкапа до правки: так видно, что тест реально ловит изменение поведения.
   Проверять на реальных данных (экспорт JSON через меню «Файл» → `_applyFullImport`) —
   по-прежнему лучший вариант, когда экспорт есть; тогда класть его в `tests/fixtures/`.
   Ранее так доказано, что смена нормы пересчитывает план (5123→228) и план подзаказа
   (3375→352).
3. **В браузере:** изменения в файле НЕ подхватываются уже открытой вкладкой при загрузке
   нового JSON через меню «Файл» — нужна **полная перезагрузка страницы** (закрыть/открыть
   `План.html` или `Ctrl+Shift+R`). Об этом всегда напоминай пользователю.

## 7. Правила работы

- **Один файл.** Правки — точечные `Edit`, с проверкой синтаксиса. Не переписывай крупные
  блоки без необходимости; сохраняй стиль соседнего кода (плотность комментариев на
  русском, имена, идиомы).
- **Проверяй факты по коду.** Если описание здесь ссылается на функцию/поле, которое мог
  измениться, — сверься с актуальным `План.html` перед советом.
- **Не агрегируй макроплан** — пользователь явно выбрал «каждая запись = отдельная строка».
- **Норма РЦ — по заказу.** Не «улучшай» так, чтобы одна норма применялась ко всем заказам
  артикула без привязки — это сознательное требование.
- **Деньги/внешние действия** (деплой, отправка наружу) — только по явному запросу.
- Отвечай пользователю по-русски. Ссылки на код — кликабельным markdown
  `[файл.html:NN](План.html#LNN)`.
- Пользователь общается прямо и эмоционально; на это нормально — фокус на сути и результате.

## 8. Известные подводные камни

- `populateModules()` ссылается на пару неопределённых функций — в браузере бросает тихую
  ошибку в самом конце, но все глобальные функции к тому моменту уже объявлены, поэтому
  приложение работает. Не «чини» это сгоряча (можно, но осторожно и отдельной задачей).
- Дубли графиков-сирот в данных (бригады без строк микроплана) — теперь скрыты в фильтрах,
  но в самих данных остаются; чистить только по запросу.
- `S.orders` без `op` → расчёты по заказу местами идут по базовому маршруту (см. §4.1).
