# План V3

Планирование швейного производства: контракты → макроплан → заказы на производство →
микроплан по дням и бригадам → графики → аналитика план/факт.

Работает в двух видах:

* **Один файл** — `План.html` открывается в браузере, данные лежат в самом браузере.
  Ни сервера, ни установки; обмен между компьютерами через экспорт/импорт JSON.
* **Серверная версия** — Django + PostgreSQL: общая база, вход по логину, роли и
  ограничение по площадкам, журнал изменений. Тот же интерфейс, переключатель
  «Серверный режим».

Ниже — установка серверной версии. Чтобы просто посмотреть, достаточно открыть
`План.html` в браузере.

> **Данных нет ни в репозитории, ни в базе.** После установки во всех таблицах ноль
> строк — включая пользователей и роли: роль заводится в тот момент, когда её
> впервые кому-то выдают. Справочники, контракты и планы вводятся через интерфейс.
>
> В git не попадают ни боевые выгрузки (там номера контрактов, объёмы и названия
> площадок), ни тестовые фикстуры, ни `.env` с паролями — см. `.gitignore`.

## Что нужно установить

Нужен только Docker — Python, PostgreSQL и остальное ставятся внутрь контейнеров.
Docker Compose **не нужен**: его нет на части серверов (в Ubuntu пакет `docker.io`
идёт без плагина), а голый `docker` есть везде, где есть Docker.

| Система | Что ставить |
|---|---|
| Windows | [Docker Desktop](https://docs.docker.com/desktop/install/windows-install/) |
| macOS | [Docker Desktop](https://docs.docker.com/desktop/install/mac-install/) |
| Linux (Ubuntu/Debian) | [Docker Engine](https://docs.docker.com/engine/install/ubuntu/) |

Проверить, что всё готово:

```bash
docker --version
docker info
```

## Установка и запуск

### Шаг 1 — скачать проект

```bash
git clone https://github.com/gurevivan/plan_v3_platform.git
cd plan_v3_platform
```

### Шаг 2 — запустить установку

```bash
bash setup.sh
```

Скрипт создаст файл `.env` с новым секретным ключом и паролем базы, поднимет
PostgreSQL, соберёт образ приложения, запустит его и применит миграции. База
останется пустой.

В первый раз сборка занимает несколько минут — скачивается образ Python.

### Шаг 3 — открыть приложение

```
http://localhost:8000
```

На удалённом сервере — `http://IP-адрес:8000` (см. раздел «Настройка для удалённого
сервера»).

## Первый вход — создание администратора

База пустая — ни данных, ни пользователей, ни ролей. Заведите первого:

```bash
docker exec -it plan-web python manage.py createsuperuser
```

Спросит логин, почту (можно пропустить) и пароль. Дальше:

1. Откройте приложение и включите **«Серверный режим»** — переключатель есть на любой вкладке.
2. Войдите под созданной учётной записью.
3. Кнопкой **«Пользователи»** в зелёной полосе заведите остальных.

> Администратор — это признак учётной записи, а не роль в списке. Он правит всё и
> раздаёт права. Снять последнего администратора нельзя: управлять правами станет некому.

## Роли и доступ

Права складываются из двух независимых вещей, и они перемножаются:

* **что человек правит** — роль;
* **где** — список площадок (ОП).

Микропланировщик Бухары правит микроплан и только по Бухаре.

| Роль | Что правит |
|---|---|
| *(роли нет)* | ничего, только смотрит — режим для аналитика или руководителя |
| Справочники | номенклатура, ОП и цеха, базы, матрица доставок |
| Заказы | контракты, заказы на производство |
| Макропланирование | макроплан, эффективность по месяцам, нормы заказов |
| Микропланирование | микроплан, графики бригад, ФРВ |

Читать можно всё в пределах своих площадок — иначе не посчиталась бы аналитика,
она берёт микроплан, макроплан, заказы и справочники сразу. Чужую площадку человек
не видит.

Кто и что менял, видно по кнопке **«Кто менял»**: дата, логин, запись и что именно
изменилось — «было 0 → стало 1234».

## Управление

Все команды выполняются в каталоге проекта.

```bash
bash setup.sh --stop      # остановить (данные остаются)
bash setup.sh --start     # запустить снова
bash setup.sh --status    # что сейчас работает
bash setup.sh --logs      # логи приложения
```

То же самое обычными командами Docker, если привычнее:

```bash
docker stop plan-web plan-db
docker start plan-db && docker start plan-web
docker ps -a --filter name=plan-
docker logs -f --tail 100 plan-web     # приложение
docker logs -f --tail 100 plan-db      # база
```

## Обновление до новой версии

```bash
git pull
bash setup.sh
```

`setup.sh` можно запускать сколько угодно раз: он пересобирает образ и
пересоздаёт приложение, **не трогая том с данными**. Отдельной инструкции по
обновлению нет намеренно — она однажды разошлась бы с установкой.

Миграции базы применяются автоматически при запуске контейнера.

> Перед обновлением на рабочем сервере снимите копию базы — `./db_backup.sh`.

## Резервное копирование

**Снять копию**

```bash
./db_backup.sh              # копия в backups/
./db_backup.sh --check      # свежесть и целостность последней
```

Хранится 48 почасовых копий (двое суток) плюс по одной на день за месяц.
Для регулярных копий добавьте в cron:

```
15 * * * * /путь/к/проекту/db_backup.sh >> /путь/к/проекту/backups/db_backup.log 2>&1
```

**Восстановить**

```bash
./db_restore.sh --list                        # какие копии есть
./db_restore.sh                               # из самой свежей
./db_restore.sh backups/plandb_….sql.gz       # из конкретной
```

Восстановление ЗАМЕЩАЕТ содержимое базы, поэтому спрашивает подтверждение и
предварительно сохраняет текущее состояние — чтобы неверно выбранный файл можно
было откатить.

## Как данные попадают в базу

Это место путает чаще всего, поэтому по шагам.

**Приложение умеет работать двумя способами, и они не смешиваются:**

| Серверный режим | Где лежат данные | Что делает «Файл» → «Загрузить» |
|---|---|---|
| **выключен** | в самом браузере (localStorage) | заменяет данные **в браузере**; база не меняется |
| **включён** | в базе на сервере | у администратора — открывает заливку в базу; у остальных — объясняет, что файл нужно отдать администратору |

Загрузка файла **всегда замещает** те разделы, что в нём есть: второй файл не
добавляется к первому, а встаёт на его место. Складывать несколько выгрузок умеет
только заливка в базу с режимом «Слить с базой».

Отсюда самая частая история: человек при выключенном режиме загружает файл,
видит справочники, включает режим или жмёт «Обновить с сервера» — и всё
«пропадает». Ничего не пропало: показывается то, что лежит **в базе**, а файл
туда не попадал. Приложение теперь предупреждает об этом до, а не после — и в
зелёной полосе всегда написано, сколько записей сейчас в базе.

**Чтобы файл попал в базу**, нужен один из двух путей:

1. В интерфейсе: войти администратором, включить серверный режим и нажать
   **«Залить файл»** (кнопка в зелёной полосе) — см. следующий раздел.
2. Из командной строки: `import_json` — там же.

**Когда данные уже в базе**, файлы больше не нужны: все правки уходят на сервер
сами, по мере работы. Кнопка «Обновить с сервера» просто перечитывает базу — она
ничего не сохраняет и не удаляет.

> Если в зелёной полосе написано «в базе: номенклатура 0, ОП 0», значит в базе
> действительно пусто — данные надо залить. Если там числа, а на вкладке пусто —
> дело в доступе по площадкам (см. «Частые ошибки»).

## Перенос данных из файла

Если работа велась в однофайловой версии, выгрузки можно залить в базу — в том
числе **несколько выгрузок с разных компьютеров**.

**Из интерфейса.** Войдите администратором, включите серверный режим и нажмите
**«Залить файл»** в зелёной полосе. Выберите JSON (меню «Файл» → «Экспорт» на том
компьютере) и режим:

* **Слить с базой** — совпадающие записи обновятся, новые добавятся. Ничего не
  пропадёт: так данные нескольких площадок собираются в одну базу.
* **Заменить всё** — прежние данные удаляются целиком. Нужно только при переносе
  с нуля.

**Проверить, нет ли в базе дублей:**

```bash
docker exec -it plan-web python manage.py find_duplicates        # показать
docker exec -it plan-web python manage.py find_duplicates --fix  # схлопнуть
```

Дублем считается совпадение делового ключа — того же, по которому работает
слияние. Перед `--fix` снимите копию: `./db_backup.sh`.

**Кто есть кто и у кого какие права:**

```bash
docker exec -it plan-web python manage.py whoami                  # список
docker exec -it plan-web python manage.py whoami --make-admin ivan  # выдать админа
```

**Из командной строки** — то же самое:

```bash
docker exec -i plan-web python manage.py import_json - --merge < выгрузка.json  # слить
docker exec -i plan-web python manage.py import_json - < выгрузка.json          # заменить всё
```

> **Как определяется дубль.** По деловому ключу, а не по внутреннему номеру
> записи: контракт — по номеру, заказ — по номеру, изделие — по артикулу ГП,
> площадка — по названию, смена микроплана — по дате вместе с ОП, переделом,
> бригадой, заказом и артикулами. Счётчик `id` в каждом браузере свой, поэтому
> запись `id=14` из двух выгрузок — это две РАЗНЫЕ записи; слияние по номеру
> смешало бы данные разных площадок. Внутренние ссылки (микроплан → бригада,
> микроплан → контракт) при заливке перенумеровываются, чтобы указывать туда же,
> куда указывали в своём файле.

> Заливка доступна только администратору. На вход нужен файл, уже открытый и
> сохранённый актуальной версией приложения: слой миграций старых форматов живёт
> в самом `План.html` и на сервере не повторяется (`DATA_CONTRACT.md`).

Обратно данные всегда можно забрать — `GET /api/export` отдаёт тот же формат, что
понимает однофайловая версия.

## Настройка для удалённого сервера

Настройки лежат в `.env` (создаётся установкой). Что стоит поменять:

```bash
PLAN_PORT=8000                     # порт, на котором открывается приложение
DJANGO_ALLOWED_HOSTS=plan.фирма.uz # домены и адреса, с которых пускать
TZ=Asia/Tashkent                   # часовой пояс
PLAN_NET=                          # сеть Docker: пусто — создать свою
```

**Про сеть.** Установка создаёт свою сеть `plan-net` — по ней приложение находит
базу по имени контейнера. Если Docker на сервере работает давно, свободные
подсети могут кончиться (`all predefined address pools have been fully
subnetted`); тогда установка сама пробует задать подсеть явно. Если и это не
проходит, впишите в `PLAN_NET` имя существующей сети — контейнеры подключатся к
ней, и ничего создавать не потребуется.

После правки:

```bash
bash setup.sh
```

Чего делать **не** нужно:

* менять `DJANGO_SECRET_KEY` на рабочем сервере — все войдут заново;
* включать `DJANGO_DEBUG=1` где-то, кроме своей машины: в отладочном режиме
  страница ошибки показывает настройки и куски кода;
* выставлять порт базы наружу — к ней ходит только приложение.

Для доступа из интернета поставьте перед приложением nginx с HTTPS: пароли и
данные не должны ходить открытым текстом.

## Частые ошибки и решения

| Что видно | Почему | Что делать |
|---|---|---|
| `port is already allocated` | порт 8000 занят другой программой | поменяйте `PLAN_PORT` в `.env` и запустите `bash setup.sh` |
| `all predefined address pools have been fully subnetted` | на сервере кончились свободные подсети Docker — обычно много старых сетей | установка сама пробует явные подсети; если не помогло: `docker network prune`, либо укажите готовую сеть в `.env` — `PLAN_NET=имя_сети` |
| Страница не открывается, `bash setup.sh --status` показывает `Exited` | приложение упало при старте | `bash setup.sh --logs` — там причина |
| `нужен PG_PASSWORD` / `нужен DJANGO_SECRET_KEY` | нет файла `.env` | запустите `bash setup.sh` |
| «Вход не выполнен» при включении серверного режима | нет учётной записи | `docker exec -it plan-web python manage.py createsuperuser` |
| Нет кнопок «Залить файл» / «Пользователи», хотя вы администратор | учётная запись на сервере не помечена администратором, либо страница ещё не узнала, кто вы | посмотрите список: `docker exec -it plan-web python manage.py whoami`. Выдать права: `... whoami --make-admin ЛОГИН`, затем Ctrl+Shift+R |
| «Нет прав на изменение раздела …» | у пользователя нет нужной роли | администратор выдаёт роль кнопкой «Пользователи» |
| «Запись изменена другим пользователем» | кто-то сохранил ту же строку раньше | нажмите «Обновить с сервера» и внесите правку заново |
| Вторая залитая выгрузка затёрла первую | заливали в режиме «Заменить всё» | восстановите из копии (`./db_restore.sh`) и залейте заново с режимом «Слить с базой» |
| Данные залиты, но на вкладках видно **не все площадки**, справочник ОП пуст | у вошедшего пользователя выданы доступы к площадкам — они режут и планы, и сам справочник ОП | посмотрите зелёную полосу: там написано, какие площадки доступны. Администратор снимает лишние в «Пользователи»; **ни одной отмеченной = все площадки** |
| Названия площадок в доступе не совпадают с теми, что в выгрузке | доступ выдавали до заливки данных | переоткройте «Пользователи» — список строится из справочника ОП, теперь он заполнен |
| «Синхронизация собирается удалить N записей» | в браузере остался прежний срез, а база уже изменилась | откажитесь и нажмите «Обновить с сервера» |
| Данные пропали после `docker volume rm plan-pgdata` | том и есть база | восстановите из копии: `./db_restore.sh` |
| Правки в `План.html` не видны | браузер держит старую версию | полная перезагрузка: `Ctrl+Shift+R` |

## Структура проекта

```
План.html              всё приложение: интерфейс и расчёты, один файл
help.html              справка и история изменений для пользователей
schema.html            схема расчётов

setup.sh               установка, обновление и управление одной командой
db_backup.sh           резервная копия базы
db_restore.sh          восстановление из копии

server/                серверная часть (Django + DRF)
  Dockerfile           образ приложения
  entrypoint.sh        ожидание базы и миграции при старте
  core/
    models.py          схема базы
    api/               эндпоинты, права, роли, журнал изменений
    calc/              расчётное ядро (перенос логики из План.html)
    services/          карта полей импорта и экспорта, срез для расчётов
    management/        команды: import_json, export_json, ensure_roles, …
  README.md            подробности серверной части

tests/                 автопроверки расчётов и серверного режима
  run.sh               прогнать всё
  fixtures/            данные для тестов (боевые — не в репозитории)

CLAUDE.md              архитектура и доменные правила
DATA_CONTRACT.md       формат выгрузки и ловушки переноса
ТЗ_серверная_версия.md техническое задание
```

## Локальная разработка (без Docker)

Нужны Python 3.12 и PostgreSQL.

```bash
python3 -m venv server_venv
./server_venv/bin/pip install -r server/requirements-dev.txt

export DJANGO_SECRET_KEY=что-угодно-для-разработки
export PG_DB=plandb PG_USER=planuser PG_PASSWORD=пароль
export PG_HOST=127.0.0.1 PG_PORT=5432

cd server
../server_venv/bin/python manage.py migrate
../server_venv/bin/python manage.py createsuperuser
../server_venv/bin/python manage.py runserver 127.0.0.1:8000
```

Приложение откроется на `http://127.0.0.1:8000` — страница и API отдаются одним
адресом намеренно: иначе браузер счёл бы запросы межсайтовыми и куки сессии
перестали бы ходить.

## Тесты

```bash
cd tests && ./run.sh                    # расчёты и серверный режим (Node, без браузера)
cd server && pytest core/api/test_api.py core/calc/test_parity.py
```

Проверяется не «эндпоинт ответил 200», а свойства, которые легко потерять: чужая
площадка не видна, правка поверх устаревшей версии не затирает чужую, пересчёт без
явного подтверждения не пишет в базу, серверное ядро считает так же, как
`План.html`. Подробнее — `tests/README.md` и `server/README.md`.
