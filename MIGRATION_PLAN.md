# План перехода «План V3» → серверная версия (Django + Postgres)

Документ описывает миграцию одностраничного приложения `План.html` (localStorage)
на серверную архитектуру. Зафиксированы выбранная конфигурация, целевая схема,
стратегия переноса расчётов и поэтапный план с проверяемыми результатами.

Статус: черновик плана. Код ещё не трогаем.

---

## 0. Выбранная конфигурация (решения пользователя)

| Развилка | Решение |
|---|---|
| **Цель** | многопользовательский доступ + надёжность/история данных + SQL-отчётность + интеграции |
| **Фронтенд** | оставить существующий vanilla-JS UI; Django = API + БД |
| **Расчётная логика** | перенести в Python (микроплан, нормы, валидации, авто-план) |
| **Модель данных** | сразу нормализовать в реляционные таблицы |

Это амбициозная, но связная конфигурация: фронт остаётся, но становится **тонким
клиентом** — все расчёты и хранение уходят на сервер.

---

## 1. Главный вызов (честная оценка)

Связка «оставить JS-UI + перенести расчёты в Python» создаёт два больших источника риска:

1. **Паритет двух реализаций расчётов.** Сейчас ~122 функции (строки 860–2900 +
   бригадо-дневные 7463–7600) считают нормы, мощность бригады-дня, авто-план,
   валидации. Их Python-порт обязан давать **бит-в-бит те же числа**, иначе план
   «поедет». Известные тонкие места, которые легко сломать при переносе:
   - норма по **переделу строки**, а не по первому совпадению (§4.2 CLAUDE.md);
   - приоритет нормы РЦ: макро → `tcRcOverrides` → `stageTimeCostFor` (§4.3);
   - пул мощности бригады-дня = Σ ФРВ×0.95×эфф, БЕЗ эфф.освоения; строки потребляют
     физ.минуты `штуки×норма/эфф.освоения` (§4.4);
   - подзаказы обязаны учитываться в остатке заказа (§4.5);
   - `learningEff > 100%` раздувает план — это **семантика, не баг** (§4.4);
   - режим «От ШЦ» — НЕ разворот цепочки; `prevStageInRoute(ШЦ)=null` (§4.6).
2. **Рерайтинг взаимодействия фронта.** 128 `save()` и 96 `renderActive()` сейчас
   работают синхронно с локальным состоянием `S`. После переноса каждый расчёт —
   сетевой round-trip. Нужна модель «сервер — источник правды, UI перерисовывается
   из ответа сервера», иначе либо тормоза, либо рассинхрон.

**Вывод:** ключ к успеху — не «переписать», а **доказать эквивалентность**. Поэтому
центральный инструмент плана — golden-master тестирование (см. §5).

## 2. Целевая архитектура

```
┌─────────────────────────┐     HTTP / JSON          ┌──────────────────────────┐
│  Браузер: План.html      │  ───────────────────►    │  Django + DRF            │
│  (vanilla JS UI)         │                          │  ├─ models (ORM)         │
│  - рендер вкладок         │  ◄───────────────────    │  ├─ services/calc/  ←порт│
│  - формы, onclick         │   данные + результаты    │  │   расчётного ядра     │
│  - api-client.js (новое)  │      расчётов            │  ├─ api/ (CRUD+recalc)   │
└─────────────────────────┘                          │  └─ auth/audit           │
                                                       └────────────┬─────────────┘
                                                                    │ ORM
                                                             ┌──────▼──────┐
                                                             │  Postgres   │
                                                             └─────────────┘
```

Слой `services/calc/` — изолированные **чистые функции** (вход: дто/срез данных,
выход: числа), без обращения к ORM внутри. Так их можно прогонять в pytest против
golden-выходов и переиспользовать в API и в отчётах.

## 3. Реляционная схема (первый срез)

Имена полей взяты из реального кода (`План.html`). Точную форму финализируем в Фазе 0
из живого JSON-экспорта.

**Справочники**
- `base` — базы (`S.bases`).
- `op` (ОП/цех) — `name` (натуральный ключ в текущем коде!), `workshop`,
  `process_type ∈ {РЦ,АЦ,ШЦ,У}`. → ввести суррогатный `id`, но хранить `name uniq`.
- `nomenclature` — `article_gp` **uniq** (инвариант §3: одна карточка = один GP),
  `name`, `model`, assortment-поля.
  - `nom_route` — базовый маршрут: `(nomenclature_id, ordinal, stage, article_item, name, time_cost)`.
  - `nom_route_override` — `(nomenclature_id, op_id)` + строки `nom_route_override_item`
    (переопределение маршрута на уровень ОП, §4.1).
- `delivery_matrix` — `(from_op_id, to_op_id, days)`.
- `holiday`, `cal_override`.

**Контур заказов**
- `contract` — `number`, `article_gp`, `name`, `quantity`, `delivery_date`;
  дочерние `contract_article_item`, `contract_deadline`, `contract_delivery_schedule`.
- `customer_order` (`S.customerOrders`).
- `production_order` (`S.orders`) — `number`, `article_gp`, `name`, `quantity`,
  `delivery_date`, `contract_num`; ОП по переделам `opRc/opAc/opSh/opU` →
  таблица связи `production_order_op (order_id, stage, op_id)` (многие-ко-многим).
  **Внимание (§4.1):** у заказа нет `op` для расчётов по базовому маршруту — учесть.
- `order_link` — `(customer_order_id, production_order_id, qty)` (`S.orderLinks`).
- `tc_rc_override` — `(order_number uniq, time_cost_min)` (норма РЦ по заказу, §4.3).

**Планы**
- `macroplan_row` — `contract_id`, `article_item`, `op_id`, `workshop`, `month`,
  `qty_sew`, `eff`, `norm_override`, `volume_type ∈ {main,extra}`; связь с заказами
  `macroplan_row_order (row_id, order_number)` (поле `orderNums`).
  **Не агрегировать** (требование §5.4б: каждая запись = отдельная строка).
- `schedule` (бригада/график) — `name`, `op_id`, `workshop`, `active_months`(JSONB/таблица);
  `schedule_month_override`.
- `microplan_row` — `date`, `op_id`, `workshop`, `stage`, `schedule_id`,
  `plan_release`, `fact_release`, `plan_release_is_manual`, `learning_eff`,
  `contract_id`, `release_order`.
  - `microplan_row_article_item` — состав строки (`articleItems`).
  - `micro_sub_order` — подзаказы (`subOrders[]`, §4.5).
  - `launch_entry` — запуски (`launchEntries[]`/`launches[]`).
  - детализация работников/ФРВ — `micro_row_worker` (из `migrateMicroplanWorkers`).
- `manual_frv` + `manual_frv_segment` + `manual_frv_pivot_extra_row` + список
  `manual_frv_extra_month`.

**Системное**
- `app_state_meta` — `next_id` и пр. (или заменить на sequence Postgres).
- `audit_log` — кто/что/когда (Фаза 5).

> Спорные места схемы (фиксируем в Фазе 0): `op` идентифицируется по `name` — при
> переименовании ОП сейчас «потеряются» ссылки; в реляционке вводим `id` и таблицы
> связи. `release_order`/`launches` — формат заказа в строке (см. `releaseOrderEq`).

## 4. Что портировать в Python (расчётное ядро)

Переносим группами, каждая закрывается parity-тестом (§5). Порядок — от листьев к корню:

1. **Даты/доставки:** `calcArrivalDate`, `addCalDays`, `prevWorkday`, `deliveryDaysFor`.
2. **Маршруты:** `routeForOp`, `allRoutesOf`, `prevStageInRoute`, `routeStagesForGp`,
   `migrateNomenclatureRouteOverrides`.
3. **Нормы:** `timeCostOf`, `timeCostForProcess`, `stageTimeCostFor`, `tcForMicroRow`,
   `tcForSubOrder`, `normFromMacroForOrder`, `macroRowLaborMinutes`.
4. **ФРВ/мощность:** `workersAvailableMinSum`, `frvEffectiveForMacroLoad`,
   `frvManualEffectiveSumOpMonth`, `brigadeDayGroupRows`, `brigadeDayPoolRawMin`,
   `brigadeDayUsedByOthersRawMin`.
5. **Авто-план (ядро):** `_recalcPlanReleaseCore`, `recalcAllMicroPlans`
   (сначала ручные `planReleaseIsManual`, потом авто — §4.4).
6. **Остатки/комплектность:** `orderStagePlannedQty`, `factByOrderStageKits`,
   `stageFactLimit`.
7. **Валидации:** `validateStageFact`, `validateStageLaunch`, `validatePlanOrderLimit`,
   `validatePlanVsPrevStagePlan`, `validateReleaseVsLaunches`, `validateFactVsOrderQty`,
   `checkDeliveryDate`.
8. **Аналитика:** агрегаты `renderAnalytics` → выносим как чистые расчёты под SQL/отчёты.

Объём: ~122 функции в основном диапазоне. Это самая длинная фаза.

## 5. Стратегия паритета (golden-master) — критично

Используем существующий VM-харнесс из CLAUDE.md §6 как «эталон»:

1. **Корпус входов.** Собрать несколько реальных JSON-экспортов (через меню «Файл»),
   включая «злые» кейсы: route overrides (ОП-5), норма РЦ по заказу, подзаказы,
   `learningEff>100%`, режим «От ШЦ», заказ на нескольких ОП.
2. **Снять эталонные выходы.** Для каждого входа прогнать JS-функции в Node
   (харнесс §6) и сериализовать результаты: пересчитанный `microplan` (план/факт по
   строкам), нормы по ключам, остатки заказов, вердикты валидаций. → `fixtures/golden/*.json`.
3. **Python-тесты.** `pytest`: загрузить тот же вход в нормализованную БД (или в
   дто), вызвать Python-порт, сравнить с эталоном с допуском (целые штуки — точно;
   минуты/проценты — округление как в JS).
4. **Регрессионный шлюз.** Ни одна группа функций не считается «перенесённой», пока
   её golden-тест не зелёный. Доказанные кейсы из §6 (норма 5123→228, подзаказ
   3375→352) — обязательные в наборе.

Это превращает рискованный перенос в проверяемый.

## 6. API-контракт (DRF)

- **CRUD** на все сущности §3 (ViewSets + сериализаторы).
- **Расчётные endpoints** (сервер — источник правды):
  - `POST /api/microplan/recalc` — пересчитать авто-план (вся сетка или срез
    бригада-день/месяц); ответ = обновлённые строки для перерисовки.
  - `POST /api/microplan/validate` — вердикты валидаций по строке/факту/запуску.
  - `GET  /api/analytics?...` — агрегаты (ОП→Передел→Бригада→Контракт→Ассорт→Артикул,
    штуки/минуты, на дату/с накоплением — как в текущем `renderAnalytics`).
- **Совместимость:** `GET /api/export` и `POST /api/import` в **том же JSON-формате**,
  что `exportAllData`/`_applyFullImport`. Это даёт путь миграции и аварийный откат.
- **Конкурентность:** ответы несут `version`/`updated_at` для оптимистичной блокировки.

## 7. Фронтенд: переключение на API (UI остаётся)

- Новый модуль `api-client.js` — замена `loadLS`/`save`:
  - `loadLS()` → загрузка состояния через `GET /api/state` (или по вкладкам, лениво).
  - `save()` (128 точек) → дебаунс-`PATCH`/транзакции. Промежуточный шаг: оставить
    `S` как клиентский кэш, синхронизировать дельтами.
- Расчёты: локальные вызовы `recalcAllMicroPlans`/`validate*` заменить на вызовы
  endpoints; UI перерисовывается из ответа. Где нужен мгновенный отклик — оптимистичное
  локальное эхо + серверная сверка (НЕ дублировать всю логику на клиенте).
- `renderActive()` (96 точек) остаётся, но данные берёт из ответа API, а не из `S`-расчётов.
- Авторизация: сессии Django вместо текущего Basic Auth в `serve.py`.

## 8. Многопользовательность, надёжность, аудит, интеграции

- **Конкурентность:** оптимистичная блокировка по `version`/`updated_at` на строках
  микроплана и макроплана; при конфликте — 409 + слияние/переспрос. Пессимистичные
  блокировки на уровне «бригада-день», если правки часто пересекаются.
- **История/аудит:** `django-simple-history` или своя `audit_log` (кто, что, до/после).
  Закрывает цель «история данных» и даёт откат версий.
- **Бэкапы:** `pg_dump` по cron заменяет `backup.sh`; PITR при необходимости.
- **SQL-отчёты:** обычные/материализованные представления поверх нормализованных
  таблиц (цель «SQL-аналитика»). Тяжёлую аналитику — в БД, не на клиенте.
- **Интеграции:** тот же DRF-API + ключи/токены для внешних систем (1С и пр.).

## 9. Поэтапный план (с проверяемыми результатами)

| Фаза | Содержание | Готово, когда |
|---|---|---|
| **0. Контракт данных** | JSON Schema всех коллекций из живого экспорта; корпус фикстур; golden-харнесс на базе §6 | эталонные выходы сняты и стабильны |
| **1. Скелет** | Django+Postgres+docker; нормализованные модели §3; команда `import_json` (живой экспорт → таблицы) + обратный `export_json` | round-trip JSON→БД→JSON эквивалентен исходному |
| **2. Расчётное ядро** | порт групп §4 в `services/calc/` с parity-тестами §5 | все golden-тесты зелёные, включая 5123→228 и 3375→352 |
| **3. API** | DRF CRUD + recalc/validate/analytics + export/import | контракт покрыт тестами, Postman/pytest-API зелёные |
| **4. Фронт на API** | `api-client.js`, замена loadLS/save/recalc; сессии | UI работает на сервере, паритет с текущим поведением вручную проверен |
| **5. Multi-user/надёжность** | блокировки, аудит, pg_dump-бэкапы | два пользователя правят без потери данных; есть история |
| **6. Отчёты/интеграции** | SQL-вьюхи, внешний API | целевые отчёты считаются в БД; интеграция отдаёт данные |

Фазы 0–2 — фундамент и наибольший риск; их нельзя срезать. Фазы 4–6 можно вести
итеративно вкладка-за-вкладкой (микроплан — последним, он самый сложный).

## 10. Риски и митигации

- **Расхождение JS↔Python в расчётах** → golden-master шлюз (§5), запрет мержить
  «красные» группы; держать обратный `export_json` для прямого diff со старым приложением.
- **UX-тормоза из-за round-trip** → серверный recalc возвращает только затронутый
  срез (бригада-день/месяц); дебаунс; оптимистичное эхо для штучных правок.
- **Идентификация ОП по `name`** → суррогатные `id` + таблицы связи; миграция
  переименований через маппинг.
- **Заказ без `op` для базового маршрута** (§4.1) → сохранить текущее поведение,
  покрыть тестом, не «чинить» молча.
- **Большой объём (~10.5k строк JS)** → переносим только расчётное ядро (~122 ф-ции);
  UI и рендер не переписываем (выбор пользователя), что снимает большую часть объёма.
- **Семантика-ловушки** (`learningEff>100%`, режим «От ШЦ» ≠ разворот) → зафиксированы
  как тест-кейсы, а не «улучшаются».

## 12. Чего НЕ делаем

- Не переписываем UI/рендер (решение пользователя — фронт остаётся).
- Не агрегируем макроплан (§5.4б / правила §7).
- Не «спрямляем» норму РЦ на все заказы артикула (§4.3 — сознательное требование).
- Не разворачиваем порядок стадий в ШЦ→АЦ→РЦ (§4.6 — грубая ошибка).
- Не трогаем латентный баг `populateModules` в рамках этой миграции (отдельная задача).
