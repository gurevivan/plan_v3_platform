# ТЗ: серверная многопользовательская версия «План V3»

Версия 1.1 от 01.08.2026. Основание: решение от 30.06.2026 (MIGRATION_PLAN.md),
доменные инварианты — CLAUDE.md, контракт данных — DATA_CONTRACT.md.

Изменения в 1.1: до 100 пользователей вместо 5–20 и роли с ограничением по ОП (§7а);
измеренная квадратичная сложность пересчёта и следствия для фазы 2 (§8);
требования к контейнеризации и репозиторию (§12).

---

## 1. Общие сведения

- **Система:** «План V3» — оперативное планирование швейного производства
  (контракты → макроплан → заказы на производство → микроплан → графики → аналитика).
- **Текущее состояние:** одностраничное приложение `План.html` (~11 700 строк,
  vanilla JS), данные в localStorage браузера, обмен через экспорт/импорт JSON.
- **Цель:** многопользовательский доступ (до 100 пользователей с разными ролями), надёжность и история данных,
  SQL-отчётность, интеграции с внешними системами (1С и др.).

## 2. Целевая архитектура

- **Бэкенд:** Django + Django REST Framework, БД PostgreSQL, развёртывание в Docker.
- **Фронтенд:** существующий vanilla-JS UI сохраняется без переписывания;
  становится тонким клиентом (новый модуль `api-client.js`).
- **Расчётная логика:** полностью переносится в Python — слой `services/calc/`
  из чистых функций (вход — срез данных, выход — числа), без ORM внутри;
  переиспользуется в API и отчётах.
- **Сервер — единственный источник правды.** UI перерисовывается из ответов API.

## 3. Требования к модели данных

Нормализовать 22 коллекции состояния `S.*` в ~30 реляционных таблиц:

**Справочники:** `base`; `op` (суррогатный `id`, `name` unique, `workshop`,
`process_type ∈ {РЦ, АЦ, ШЦ, У}`); `nomenclature` (`article_gp` unique — инвариант:
одна карточка = один GP) с `nom_route` (базовый маршрут) и `nom_route_override`
(переопределения маршрута на уровень ОП); `delivery_matrix`; `holiday`, `cal_override`.

**Контур заказов:** `contract` (+ артикулы, дедлайны, график поставок);
`customer_order`; `production_order` — у заказа НЕТ единого поля op, ОП по переделам
через таблицу связи `production_order_op (order_id, stage, op_id)`; `order_link`;
`tc_rc_override (order_number unique, time_cost_min)` — индивидуальная норма РЦ по заказу.

**Планы:** `macroplan_row` (+ связь с заказами `macroplan_row_order`; записи НЕ
агрегируются — каждая введённая запись отдельная строка); `schedule` (бригады,
`active_months`); `microplan_row` (+ `microplan_row_article_item`, `micro_sub_order`
— подзаказы, `launch_entry`, `micro_row_worker`); `manual_frv` с сегментами.

**Системное:** последовательности Postgres вместо `next_id`; `audit_log`.

Физический поток стадий всегда РЦ → АЦ → ШЦ → У → База (АЦ может отсутствовать).

## 4. Требования к расчётному ядру (Python-порт)

Перенести ~122 функции группами, от листьев к корню:
1. Даты/доставки: `calcArrivalDate`, `addCalDays`, `prevWorkday`, `deliveryDaysFor`.
2. Маршруты: `routeForOp`, `allRoutesOf`, `prevStageInRoute`, `routeStagesForGp`.
3. Нормы: `stageTimeCostFor`, `tcForMicroRow`, `tcForSubOrder`,
   `normFromMacroForOrder`, `macroRowLaborMinutes`.
4. ФРВ/мощность: `workersAvailableMinSum`, `brigadeDayGroupRows`,
   `brigadeDayPoolRawMin`, `brigadeDayUsedByOthersRawMin`.
5. Авто-план: `_recalcPlanReleaseCore`, `recalcAllMicroPlans` (сначала ручные
   строки, потом авто).
6. Остатки/комплектность: `orderStagePlannedQty`, `factByOrderStageKits`, `stageFactLimit`.
7. Валидации: `validateStageFact`, `validateStageLaunch`, `validatePlanOrderLimit`,
   `validatePlanVsPrevStagePlan`, `validateReleaseVsLaunches`, `validateFactVsOrderQty`.
8. Аналитика: агрегаты `renderAnalytics` как чистые расчёты/SQL.

**Обязательные к сохранению инварианты (семантика, не баги):**
- норма берётся по переделу строки, не по первому совпадению артикула;
- приоритет нормы РЦ: макрострока с привязанным заказом → `tc_rc_override` →
  норма стадии → общая; норма РЦ индивидуальна по заказу, не «спрямлять»;
- пул мощности бригады-дня = Σ ФРВ × 0.95 × эфф. работников, БЕЗ эфф. освоения;
  строка потребляет физ.минуты = штуки × норма / эфф. освоения;
- остаток заказа по переделу учитывает main-строки И подзаказы других строк;
- `learningEff` до 200%, >100% раздувает план сверх физической мощности — так задумано;
- режим «От ШЦ» — не разворот цепочки: ШЦ планируется первым как якорь,
  upstream-проверки к ШЦ не применяются; порядок стадий не менять.

   норма из макроплана, подзаказы, перевыполнение и недовыполнение, переделы РЦ/ШЦ/У.

2. Эталонные выходы снимаются прогоном текущих JS-функций в Node (VM-харнесс) →

3. pytest: тот же вход в БД/дто → Python-порт → сравнение с эталоном

4. Группа функций считается перенесённой только при зелёном golden-тесте.
   Обязательные кейсы: пересчёт нормы 5123→228, подзаказ 3375→352.

## 6. Требования к API (DRF)

- CRUD на все сущности §3 (ViewSets + сериализаторы).
- Расчётные endpoints:
  - `POST /api/microplan/recalc` — пересчёт авто-плана (вся сетка или срез
    бригада-день/месяц), ответ — обновлённые строки;
  - `POST /api/microplan/validate` — вердикты валидаций по строке/факту/запуску;
  - `GET /api/analytics` — агрегаты (ОП → Передел → Бригада → Контракт →
    Ассорт. группа → Артикул; штуки/минуты; на дату/с накоплением).
- Совместимость: `GET /api/export` и `POST /api/import` в том же JSON-формате,
  что текущие `exportAllData` / `_applyFullImport` (путь миграции и аварийный откат).
- Ответы несут `version` / `updated_at` для оптимистичной блокировки.

## 7. Фронтенд: перевод на API

- `api-client.js`: `loadLS()` → `GET /api/state` (лениво по вкладкам);
  133 точки `save()` → дебаунс-PATCH; `S` остаётся клиентским кэшем,
  синхронизация дельтами.
- Локальные вызовы `recalcAllMicroPlans` / `validate*` → вызовы endpoints;
  99 точек `renderActive()` остаются, но данные — из ответа API.
  Расчётную логику на клиенте НЕ дублировать; где нужен мгновенный отклик —
  оптимистичное эхо + серверная сверка.
- Авторизация: сессии Django (логин/пароль).

## 7а. Роли и права доступа

До **100 одновременных пользователей** с разными функциями: одни ведут макроплан,
другие микроплан, третьи только смотрят аналитику. Роль определяет не только
«что можно делать», но и **над какими ОП** — мастер площадки правит микроплан своих
бригад, а не чужих.

**Сделано 02.08.2026.** Роли получились компактнее задуманного: вместо шести
названий должностей — четыре набора прав на разделы плана. Должность
складывается из роли и списка площадок, и держать её отдельной сущностью значит
хранить одно и то же дважды.

| Роль | Что правит | Кому |
|---|---|---|
| — (роли нет) | ничего, только смотрит | аналитик, руководитель |
| Справочники | номенклатура, ОП и цеха, базы, матрица доставок | технолог, нормировщик |
| Заказы | контракты, заказы на производство | снабжение, сбыт |
| Макропланирование | макроплан, эффективность по месяцам, нормы заказов | планировщик |
| Микропланирование | микроплан, графики бригад, ФРВ | мастер, начальник цеха |

**Администратор — не роль, а признак учётной записи** (`is_superuser`). Иначе
получилось бы два места, где написано одно и то же, и они разошлись бы: сняли
галочку в одном, забыли в другом — и непонятно, админ человек или нет.
Администратор может назначить администратором другого; снять последнего нельзя —
управлять правами станет некому.

**Раздел и площадка перемножаются.** Роль отвечает на вопрос «что», `UserOpAccess`
— «где». Право на запись есть только там, где разрешено и то, и другое:
микропланировщик Бухары правит микроплан и только по Бухаре.

**Ограничивается запись, но не чтение.** Аналитика считается по микроплану,
макроплану, заказам и справочникам сразу; запрет читать раздел сломал бы её
тому, кому её как раз и открыли. Чужую площадку человек всё равно не видит —
это режется по ОП.

**Ограничение по ОП — часть модели данных, а не проверка в интерфейсе.** Нужна
связь «пользователь ↔ доступные ОП» (`user_op_access`) и фильтрация в QuerySet на
уровне API, иначе любой запрос в обход UI отдаст чужие данные. Ретроспективно это
прикручивается тяжело — закладывать в фазе 1 вместе с моделями.

**Побочная выгода для конкурентности:** пересечения правок редки не потому, что
пользователей мало, а потому что они работают в разных ОП и разных сущностях.
Поэтому оптимистичной блокировки по `version` достаточно; пессимистичные блокировки
уровня «бригада-день» вводить только если практика покажет реальные конфликты.

## 8. Многопользовательность и надёжность

- Оптимистичная блокировка по `version`: конфликт → HTTP 409 + переспрос;
  при частых пересечениях — пессимистичная блокировка уровня «бригада-день».
- Аудит: `django-simple-history` или `audit_log` (кто, что, когда, до/после);
  возможность отката.
- Бэкапы: `pg_dump` по cron, хранение вне сервера; восстановление отработано.
- Производительность: пересчёт среза бригада-день/месяц ≤ 1–2 с; интерактивные
  правки без заметных задержек (дебаунс + частичный recalc). Расчёт на **до 100
  одновременных пользователей** (см. §7а — большинство работает в разных ОП и
  разных вкладках, одновременных правок одной сущности мало).

### Измерено на боевых данных (01.08.2026) — обязательно учесть в фазе 2

Замер на реальной фикстуре (315 строк микроплана) в Node-харнессе:

| Строк микроплана | Полный `recalcAllMicroPlans` |
|---|---|
| 315 | 0,15 с |
| 630 | 0,58 с |
| 1 260 | 2,3 с |
| 2 520 | 9,2 с |

**Сложность квадратичная:** удвоение данных даёт четырёхкратный рост. Причина —
`orderStagePlannedQty` и соседние функции сканируют весь `S.microplan` при каждом
вызове, а вызываются они по несколько раз на строку (в файле 5 мест со сплошным
перебором микроплана).

Следствия, которые нельзя игнорировать:

1. **Полный пересчёт на сервере по каждому сохранению недопустим.** При 20 площадках
   и годовом горизонте счёт идёт на десятки минут. Частичный пересчёт (бригада-день,
   максимум месяц) — не оптимизация, а обязательное требование.
2. **В Python-порте перебор заменить индексом.** Один проход строит
   `{(заказ, передел): [строки]}`, дальше выборки по ключу — это переводит пересчёт
   из O(n²) в O(n). Индекс строится на срез, а не на всю таблицу.
3. **Считать в БД, а не в памяти процесса.** Суммы «покрыто по заказу+переделу»
   естественно ложатся на агрегаты SQL с индексом по `(release_order, stage, date)`.
4. Golden-тест на этой же фикстуре гарантирует, что оптимизация не изменит числа:
   на реальных данных пересчёт совпадает с сохранённым планом построчно (315 из 315).

## 9. Этапы, сроки, критерии готовности

| Фаза | Содержание | Готово, когда | Оценка |
|---|---|---|---|
| 0 | JSON Schema, фикстуры, golden-харнесс | эталоны сняты и стабильны | 60–80 ч |
| 1 | Django+Postgres+Docker, модели, import/export | round-trip JSON→БД→JSON эквивалентен | 80–120 ч |
| 2 | Порт расчётного ядра + parity-тесты | все golden-тесты зелёные | 200–280 ч |
| 3 | DRF: CRUD + recalc/validate/analytics | контракт покрыт тестами | 80–120 ч |
| 4 | Фронт на API, сессии | UI работает от сервера, паритет проверен | 120–200 ч |
| 5 | Блокировки, аудит, бэкапы | двое правят без потери данных | 70–90 ч |
| 6 | SQL-отчёты, внешний API | отчёты считаются в БД | 40–80 ч |

Итого 650–970 ч чистыми, 750–1150 ч с буфером 15–20%. Фазы 0–2 не срезать;
фазы 4–6 — итеративно, вкладка за вкладкой, микроплан последним.

## 10. Ограничения (чего НЕ делаем)

- Не переписываем UI/рендер и не вводим фреймворки/сборщики на фронте.
- Не агрегируем макроплан.
- Не применяем одну норму РЦ ко всем заказам артикула.
- Не разворачиваем порядок стадий (ШЦ→АЦ→РЦ — грубая ошибка).
- Латентную особенность `populateModules()` в рамках миграции не трогаем.

## 11. Требования к сопровождаемости (снижение риска «одного человека»)

Цель: система должна поддерживаться посторонним специалистом среднего уровня,
а не только автором.

1. **Только мейнстрим-стек.** Django + DRF + Postgres + Docker, без экзотических
   библиотек и самописных «умных» решений. Любое отступление — с обоснованием в ADR.
2. **Тесты как носитель знания.** Golden-master набор (§5) обязателен к поддержанию:
   ни одна доработка не принимается без зелёных тестов. Все семантические ловушки
   (§4) зафиксированы тест-кейсами, а не устной традицией.
3. **Код и доступы у компании.** Git-репозиторий на аккаунте организации
   (или self-hosted Gitea на своём сервере); пароли, ключи, доступы к серверу,
   домену и бэкапам — в менеджере паролей компании.
4. **Runbook.** Документ «как задеплоить с нуля, как восстановить из бэкапа,
   типовые сбои и действия». Критерий приёмки: посторонний человек по runbook
   поднимает систему из бэкапа за час; процедура реально прогнана минимум один раз.
5. **Аварийный люк по данным.** Экспорт в текущем JSON-формате (§6) сохраняется
   всегда: данные можно выгрузить и вернуться к автономному `План.html`.
6. **Второй человек.** Минимум: сотрудник, умеющий «восстановить из бэкапа и
   перезапустить» + договор поддержки с внешним исполнителем на 5–10 ч/мес,
   ознакомленным с проектом заранее.
7. **Документация — артефакт каждой фазы:** архитектура, инварианты домена,
   runbook, ADR по нестандартным решениям. Поддерживается связка
   «новый специалист + ИИ-ассистент» (CLAUDE.md и тесты — точка входа), но как
   дополнение к пп. 1–6, не замена.

## 12. Развёртывание, контейнер и репозиторий

**Сейчас:** тот же сервер, что и текущий `serve.py` (порт 8090, systemd).

**Потом:** упаковка в Docker и публикация в Git-репозиторий. Требования, которые
из-за этого надо соблюдать с самого начала:

- **Конфигурация только через переменные окружения** — секретов в коде нет.
  Уже сейчас `serve.py` читает `PLAN_PORT` / `PLAN_USER` / `PLAN_PASS` из окружения;
  Django-часть строить так же (`SECRET_KEY`, параметры БД, `ALLOWED_HOSTS`).
- **Боевые данные в репозиторий не попадают.** Экспорты содержат номера контрактов
  и заказов, объёмы, названия площадок. `.gitignore` исключает `tests/fixtures/*.json`,
  `tests/fixtures/golden/`, `backups/`, `screenshots/`. Фикстуры передаются напрямую,
  эталоны снимаются на месте (`node golden_snapshot.js`). См. `tests/fixtures/README.md`.
- **Состав образа:** Django + gunicorn, Postgres отдельным сервисом, nginx для статики
  и TLS. `docker-compose.yml` для разработки, отдельный compose или манифест для боя.
- **Миграции БД применяются на старте контейнера**, данные живут в volume — образ
  остаётся stateless и заменяемым.
- HTTPS и домен — на этапе выхода за периметр сервера; до тех пор Basic Auth заменяется
  сессиями Django (§7).
