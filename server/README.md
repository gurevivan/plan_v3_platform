# Серверная версия «План V3»

Django + DRF + PostgreSQL.

Фаза 1 закрыта: нормализованная схема, импорт JSON-экспорта в базу и выгрузка
обратно, круговой рейс эквивалентен исходнику. Фаза 2 в работе: расчётное ядро
переносится группами, пять из восьми готовы.

## Запуск с нуля

```bash
cd /root/plan

# 1. База (контейнер с урезанной памятью — на сервере её мало)
docker start plan-pg          # уже создан; заново — команда ниже

# 2. Миграции
cd server && ../server_venv/bin/python manage.py migrate

# 3. Загрузка данных
../server_venv/bin/python manage.py import_json ../tests/fixtures/real_export_20260801.json
```

Создание контейнера заново, если его удалили:

```bash
docker run -d --name plan-pg \
  -e POSTGRES_PASSWORD=planpass -e POSTGRES_USER=planuser -e POSTGRES_DB=plandb \
  -p 127.0.0.1:5433:5432 --memory=384m --memory-swap=512m \
  -v plan_pgdata:/var/lib/postgresql/data \
  postgres:16-alpine \
  -c shared_buffers=32MB -c max_connections=30 -c work_mem=2MB -c maintenance_work_mem=32MB
```

Порт 5433, а не 5432 — чтобы не столкнуться с чужим Postgres на сервере.
Данные в volume `plan_pgdata`, контейнер можно пересоздавать.

## Команды

| Команда | Что делает |

| `manage.py import_json ФАЙЛ` | Загрузить JSON-экспорт в базу (по умолчанию с очисткой; `--keep` не чистить) |

## Устройство

- `core/models.py` — схема. У каждой модели `src_id` (идентификатор из исходного
  JSON) и `extra` (JSONB с полями, которые не разложены по колонкам).
- `core/services/mapping.py` — единая карта «поле JSON ↔ колонка». Импорт и
  экспорт ходят через неё, поэтому разойтись не могут.
- `core/management/commands/` — три команды выше.

Два механизма, без которых круговой рейс не сходился:

**`extra['__absent']`** — список полей, которых в исходной записи не было.
Экспорт их не выводит. Иначе каждой записи дописывались бы поля со значениями по
умолчанию, и настоящие потери тонули бы в этом шуме.

**`extra['__null']`** — поля, которые были, но со значением `null`. Это не то же
самое, что отсутствие: экспорт обязан вернуть именно `null`, а не `0`.

**Значения по умолчанию в карте полей** задаются там, где домен трактует отсутствие
не как нуль. Главный пример: `learningEff` нет у большинства строк микроплана, и
приложение читает это как 100 % — записать 0 значило бы обнулить эффективность
освоения и сломать расчёт.

### Мутационная проверка

Зелёные тесты сами по себе ничего не доказывают — важно, ловят ли они ошибки.
Порт проверен подменами (каждая возвращается сразу после прогона):

| Подмена | Поймана |
|---|---|
| Банковское округление вместо `Math.round` | да |
| Другая формула множителя освоения | да |
| Авто-строки считаются раньше ручных | да |
| Пул не уменьшается на занятое другими строками | да |
| Не вычитается план того же дня из остатка заказа | да |
| Лимит комплекта = сумма вместо минимума | да |
| Проверка плана стала блокирующей (warn → stop) | да |
| Выпуск сверх суммы запусков не ловится | да |
| Упаковка считается не комплектом (фильтр артикула) | **нет** — см. ниже |
| Предыдущий передел жёстко «АЦ» вместо маршрута | да |
| Ёмкость предыдущего передела не делится по датам | да |
| «От ШЦ»: ШЦ проверяется как обычный передел | да |
| В тексте код артикула вместо названия изделия | да |
| Проверка запуска не пропускает РЦ | **равнозначная** — см. ниже |
| Узлы изделия складываются вместо минимума | да |
| Передел агрегации — первый вместо самого глубокого | да |
| РЦ-норма по заказу применяется на всех переделах | да |
| Ручная норма строки макроплана игнорируется | да |

Почти все эти подмены ловятся только благодаря синтетике: в боевых данных нет ни
нескольких строк в бригаде-дне, ни двух бригад на одном заказе в один день, ни
запусков, ни изделий из нескольких частей.

Последняя подмена НЕ ловится осознанно. Отличие проявляется, только если у одного
заказа на упаковке есть строки с разными артикулами, а маршрут даёт для У один.
Ветка защитная; подгонять под неё фикстуру значило бы закрепить в эталоне данные,
которых не бывает.

Подмена «проверка запуска не пропускает РЦ» не ловится, потому что она
**равнозначная**, а не потому что тестов не хватает: на РЦ нет предыдущего
передела, `stage_fact_limit` возвращает `None`, и проверка отдаёт OK и без раннего
выхода. Проверено отдельно, а не принято на глаз.

**Байт-код при таких проверках надо отключать** (`PYTHONDONTWRITEBYTECODE=1`).
Подмена и откат укладываются в одну секунду, а размер файла не меняется — Python
считает `.pyc` актуальным и берёт старый. Один раз это уже дало ложный вывод
«подмена не ловится».

### Паритет

```bash
cd tests && node golden_calc.js                            # эталоны с боевых данных
cd tests && node golden_calc.js synthetic_capacity.json    # эталоны с синтетики
cd server && ../server_venv/bin/python -m pytest core/calc/test_parity.py -q
```

Эталоны — не «план целиком», а выходы отдельных функций, чтобы при расхождении
было видно, в какой именно. Тесты идут по **двум** фикстурам.

**Зачем синтетика.** Боевые данные покрывают не всё: в них каждая бригада-день
содержит ровно одну строку, эффективность освоения везде 100 %, все смены 480 мин,
все цеха типа БП. То есть деление пула между строками — центральная функция
мощности — не проверялось бы вообще. `synthetic_capacity.json` закрывает именно
эти ветки: несколько строк в бригаде-дне, освоение 50/80/120 %, смены 480/600/720,
оба типа цеха, переопределение маршрута на уровень ОП, нормы РЦ и ШЦ по заказу.
Коммерческих данных не содержит, поэтому лежит в репозитории.

Синтетика здесь законна: сверяются две реализации между собой, а не расчёт с
реальностью.

**Эталон несёт состояние, на котором посчитан** (`golden/…state.json`). Импорт в
приложении прогоняет миграции и пересчёт, поэтому авто-строки могут отличаться от
того, что лежит в файле фикстуры. На боевых данных разницы нет — пересчёт
воспроизводит сохранённое построчно, — а на синтетике есть, и без этого Python
сравнивался бы с результатом чужого пересчёта.

### Зачем индекс в `Snapshot`

Главное отличие от JS-версии. Там `orderStagePlannedQty` при каждом вызове
перебирает весь микроплан, поэтому полный пересчёт растёт квадратично
(9,2 с на 2520 строк). Здесь индекс `(заказ, передел)` строится один раз при
сборке среза, и выборка становится обращением по ключу.

Замер одной и той же операции (покрытие заказа) при реалистичном росте — больше
заказов, а не копий одного:

| Строк микроплана | JS | Python с индексом |
|---|---|---|
| 315 | 41 мкс | 3,2 мкс |
| 1 260 | 153 мкс | 3,2 мкс |
| 5 040 | 634 мкс | 3,2 мкс |
| 10 080 | 1 309 мкс | 3,3 мкс |

JS растёт линейно на запрос — 32-кратный рост данных даёт 32-кратный рост времени
(41 → 1 309 мкс). Отсюда квадратичность полного пересчёта: запросов тоже становится
больше. Python держит константу, разрыв на 10 тысячах строк — почти 400-кратный.
Сборка среза линейна: 15 мс на 10 080 строк.

## Интерфейс на API (фаза 4, первая вкладка)

`План.html` отдаётся ЭТИМ ЖЕ сервером — `http://адрес:порт/`. Один адрес для
страницы и API снимает вопрос CORS и кук сессии; к тому же так и задумано в ТЗ §12
(nginx отдаёт статику, Django — API). Наружу отдаются только `План.html`,
`help.html` и `schema.html`, каталог не листается.

**Вкладка «Справочники» переведена целиком** — номенклатура, ОП и цеха, базы,
матрица доставок. Переключатель стоит над всеми четырьмя подвкладками
и по умолчанию выключен: пока он выключен, приложение работает ровно как раньше,
из localStorage, и ни одного запроса наружу не делает. Так перевод идёт вкладка за
вкладкой, не ломая остальные.

Что умеют вкладки в серверном режиме: чтение списка (со сборкой всех страниц),
создание, правка, удаление, кнопка «Обновить с сервера», показ текущего
пользователя и его прав.

**Как переводится следующая сущность.** В `План.html` есть таблица `SRV_ENTITIES`:
адрес, коллекция в состоянии и пара функций перевода формата. Логика запросов,
конфликт версий и сообщения об ошибках общие (`srvLoad`, `srvCreate`, `srvUpdate`,
`srvDelete`). Добавить сущность — это строка в таблице плюс три вставки
`if (SRV.on) …` в обработчики вкладки.

**Конфликт версий обрабатывается явно.** Правка уходит вместе с версией, которую
видел пользователь. Если карточку успел изменить кто-то другой, сервер отвечает
409, приложение перечитывает список и говорит об этом прямо — вместо того чтобы
затереть чужую правку молча.

Тесты клиента — `tests/test_server_mode.js` (33 проверки). Сеть подменяется:
проверяется не то, что отвечает сервер, а что приложение отправляет, как переводит
форматы и что делает при конфликте, отказе в правах и постраничной выдаче.

## Роли и пользователи

Кто что правит. Два независимых измерения, и они перемножаются:

* **что** — раздел плана. Хранится ролями (группы Django).
* **где** — площадка (ОП). Хранится в `UserOpAccess`.

Право на запись есть только там, где разрешено и то, и другое: микропланировщик
Бухары правит микроплан и только по Бухаре.

| Роль | Правит |
|---|---|
| — (роли нет) | ничего, только смотрит |
| `Справочники` | номенклатура, ОП и цеха, базы, матрица доставок |
| `Заказы` | контракты, заказы на производство, связи ЗК↔ПЗ |
| `Макропланирование` | макроплан, эффективность по месяцам, нормы по заказам |
| `Микропланирование` | микроплан, графики бригад, правки дней, ФРВ |

**Администратор — не роль, а признак учётной записи** (`is_superuser`). Он правит
всё и управляет людьми. Роли «Администратор» нет намеренно: два места с одним и
тем же смыслом однажды разойдутся, и станет непонятно, админ человек или нет.

```bash
../server_venv/bin/python manage.py createsuperuser   # первый администратор
```

Дальше — из интерфейса: кнопка «Пользователи» в полосе серверного режима,
видна администратору. Там заводятся люди, выдаются роли и площадки, назначаются
другие администраторы.

**Групп ролей в базе после установки нет** — список ролей живёт в коде
(`core/api/roles.py`), а группа создаётся в тот момент, когда роль впервые кому-то
выдают. Так после развёртывания в базе не остаётся ни одной строки. Если роли
нужно увидеть в админке Django заранее, их можно создать:

```bash
../server_venv/bin/python manage.py ensure_roles
```

**Что нельзя:**

* Снять последнего активного администратора — ни галочкой, ни деактивацией, ни
  удалением. Иначе управлять правами станет некому и придётся лезть в консоль.
* Стать администратором через `is_staff`. Это признак доступа в админку Django;
  права проверяет `IsSystemAdmin` по `is_superuser`. Штатный DRF'овский
  `IsAdminUser` здесь не годится — он смотрит именно на `is_staff`.
* Править доступы к ОП отдельной точкой: `/api/access` убран, они правятся только
  внутри `/api/users/{id}`. Два пути записи в одну таблицу — та же болезнь, что
  две карты полей.

**Ограничивается запись, но не чтение.** Аналитика считается на клиенте по
микроплану, макроплану, заказам и справочникам сразу — запрет читать раздел
сломал бы её тому, кому её как раз и открыли. Чужую площадку человек всё равно
не видит: чтение режется по ОП.

**Раздел эндпоинта не задаётся руками.** `urls.py` выводит его из пути роутера по
карте `SECTION_BY_PREFIX` в `core/api/roles.py`. Новый путь, не отнесённый ни к
одному разделу, роняет импорт — иначе он молча оказался бы открыт всем на запись.

Проверка: `pytest core/api/test_api.py` (45) и `tests/test_server_roles.js` (44).
Ловят ли эти тесты поломку — проверено подменами: 8 серверных и 5 клиентских.

## Журнал изменений

Отвечает на вопрос «кто поставил этот план». Читается через `/api/changes` и
кнопкой «Кто менял» в полосе серверного режима.

```
GET /api/changes/?entity=microplan&src_id=403   # история одной строки
GET /api/changes/?user=иван&since=2026-08-01    # что делал человек
```

**Хранится разница, а не копия записи** — `{поле: [было, стало]}`. Готовые
решения (`django-simple-history` и подобные) кладут полный снимок строки на
каждое сохранение; на микроплане такие снимки быстро перевесили бы сами данные,
да и это те же данные во второй раз.

Что важно и почему:

* **Точка записи одна** — `VersionedSerializer` и `perform_destroy`. Расставлять
  вызовы по обработчикам нельзя: их десятки, и забытый обработчик означал бы
  правку без следа — заметную только когда след понадобится.
* **Сохранение без изменений не пишется.** Интерфейс отправляет запись целиком
  при каждом уходе из поля; записи «ничего не изменил» сделали бы журнал
  нечитаемым.
* **Массовая операция — одна запись.** Пересчёт месяца трогает сотни строк.
* **Удаление пишется до самого удаления**, и запись не ссылается на строку
  внешним ключом: строки уже нет, а след того, кто её убрал, обязан остаться.
* **Журнал режется по ОП**, иначе через историю было бы видно площадки,
  закрытые в самих таблицах.
* **Правится только сервером** — эндпоинт доступен на чтение, история не
  редактируется.

Журнал растёт непрерывно. Очистка:

```bash
../server_venv/bin/python manage.py prune_changes --days 180        # показать
../server_venv/bin/python manage.py prune_changes --days 180 --yes  # удалить
```

## Резервные копии базы

`/root/plan/db_backup.sh` — `pg_dump` контейнера `plan-pg` с ротацией, по cron
каждый час в 15 минут. `backup.sh` (тоже по cron) копирует только `План.html` и
базы не касается — это разные вещи, и смешивать их нельзя: упавший дамп не должен
лишать нас копии файла.

```bash
/root/plan/db_backup.sh            # снять копию
/root/plan/db_backup.sh --check    # свежесть и целостность последней
```

Хранится 48 почасовых копий (двое суток) плюс по одной на день за месяц.

**Восстановление (данные будут ЗАМЕЩЕНЫ):**

```bash
gunzip -c backups/plandb_ГГГГММДД_ЧЧММСС.sql.gz | \
  docker exec -i plan-pg psql -U planuser -d plandb
```

Две вещи, из-за которых копия может оказаться бесполезной именно тогда, когда
нужна, и обе закрыты:

* **Оборванный дамп под правильным именем.** Пишем в `.part` и переименовываем
  только при успехе, дополнительно проверяя размер: `pg_dump | gzip` не вернёт
  ошибку первой команды, поэтому одного кода возврата мало.
* **Молча сломавшийся cron.** Состояние копий попадает в ежедневный отчёт
  теневой сверки. Если новых выгрузок нет, отчёт обычно не уходит вовсе — но при
  беде с копиями уходит всё равно, иначе о ней узнали бы при восстановлении.

Проверено восстановлением в отдельную базу: число записей совпало по микроплану,
макроплану, заказам, номенклатуре, пользователям и ролям.

## Теневая сверка (вариант А)

Люди работают как работали, сервер раз в день проверяет себя на свежей выгрузке.

```bash
/root/plan/shadow_check.sh                 # разобрать новые файлы от бота
/root/plan/shadow_check.sh --file ФАЙЛ     # конкретный файл
/root/plan/shadow_check.sh --no-telegram   # без отчёта
```

По cron: `30 6 * * *`, лог в `backups/shadow_check.log`, отчёт в Telegram.

**Как попадает выгрузка.** Вы отправляете JSON боту, он кладёт файл в
`/root/bot_agent/tg_img/`. Сверка сама находит новые файлы, отличает выгрузки
«Плана» от прочего по составу ключей и не берёт дважды один и тот же — признак
«уже проверяли» хранится в `ImportRun`, там же остаётся история.

**Проверяются два независимых свойства:**

| Что | Что означает расхождение |
|---|---|
| Паритет расчёта: пересчёт Python-ядром против плана в файле | серверное ядро считает не так, как приложение |
| Круговой рейс: импорт в базу → выгрузка → сравнение | слой хранения теряет данные |

Одного мало: паритет расчёта не заметит потерянного при записи поля, а круговой
рейс не заметит неверно посчитанного плана. Обе половины проверены поломкой —
испорченный план в файле и намеренная потеря коллекции при выгрузке ловятся.

**Внимание:** без `--keep-db` сверка ЗАМЕЩАЕТ содержимое базы данными из файла.
Это теневая инсталляция, её база и есть копия боевых данных.

## Серверный режим интерфейса (фаза 4)

Все видимые вкладки «Плана» умеют читать и писать через API. Включается
переключателем «Серверный режим» на любой вкладке; по умолчанию выключен.

Две вещи, которые API обязан отдавать помимо колонок, — иначе интерфейс,
сохранив запись, молча её обеднит:

| ключ | что это | чем грозит потеря |
|---|---|---|
| `absent_fields` | поля, которых в исходной записи не было (`extra['__absent']`) | пустая смена работника станет настоящими 480 вместо «как у ОП» — минус треть мощности дня |
| `null_fields` | поля, которые были со значением `null` (`extra['__null']`) | выгрузка вернёт 0 вместо `null` |
| `extra_fields` | всё, что не разложено по колонкам | пропадёт состав работников на конкретный день (`calOverrides[].workers`) |

Дочерние записи (работники, подзаказы, варианты ФРВ, строки маршрута) отдают то
же самое — см. `ChildSerializer`.

Ещё два правила, найденных живой сверкой:

- **Пропавшие дочерние записи удаляются ДО создания новых** (`_write_nested`).
  У ОП заказа ограничение (заказ, передел, ОП), а интерфейс шлёт их без
  идентификаторов — при обратном порядке вторая же отправка падает 500.
- **`trim_whitespace=False`.** DRF по умолчанию режет пробелы, и сохранение
  превращало «Футболка » в «Футболка».

### Живая проверка

```bash
tests/live_reset.sh                       # залить фикстуру и поднять сервер на 8011
cd tests && node live_api_check.js        # прогнать состояние туда и обратно
cd server && ../server_venv/bin/python manage.py compare_json \
    ../tests/fixtures/real_export_20260801.json /tmp/live_after_push.json
```

Обе сверки (`live_from_api.json` и `live_after_push.json`) должны сказать
«эквивалентен». Это единственный вид проверки, который ловит поле, которое
интерфейс читает, но не отправляет обратно: тест с подменённой сетью такую
потерю подтвердит как «работает».
