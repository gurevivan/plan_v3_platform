1. Что это

План.html — одностраничное веб-приложение (~11 800 строк: HTML+CSS+ванильный JS в одном файле). Назначение: оперативное планирование швейного производства по цепочке контракты → макроплан → заказы на производство → микроплан → график → аналитика.

Поток переделов ВСЕГДА: РЦ → АЦ → ШЦ → У → База (Раскрой → Автоматизация → Швейный цех → Упаковка → База). АЦ может отсутствовать в маршруте.

2. Стек и ограничения

  • Чистый HTML/CSS/JS, всё в одном файле. Без сборщиков, фреймворков, ES-модулей.
  • Состояние — глобальный объект S, хранится в localStorage (prod-plan-v6) + резерв IndexedDB. Обмен между компьютерами — экспорт/импорт JSON (меню «Файл»).
  • Все функции глобальные (навешаны на инлайновые onclick/onchange).
  • Сервер: serve.py (Basic Auth, порт 8090), запуск через systemd plan-html.service. Логин/пароль: plan / plan.
  • Схема данных отдельной страницей: schema.html.

4. Ключевые архитектурные решения

Маршрут на уровень ОП.
Разные ОП могут иметь разные маршруты для одного изделия без дублирования карточек (routeOverrides). Резолверы routeForOp, allRoutesOf.
Норма — по переделу строки.
Один артикул может встречаться на нескольких переделах; норма всегда берётся по стадии строки (stageTimeCostFor, tcForMicroRow).
Индивидуальная норма по заказу (РЦ и ШЦ).
У каждого заказа может быть своя норма кроя (РЦ) и пошива (ШЦ). Задаётся в макроплане (для привязанных заказов) или inline в строке микроплана. Приоритет: макроплан → inline-override → номенклатура.
Авто-план микроплана = пул мощности бригады-дня.
Мощность смены = ФРВ × 0.95 (абсентеизм) × эфф.; делится между строками/подзаказами дня; штуки = минуты / норма / эфф.освоения.
План НЕ реагирует на факт.
План — то, что запланировали; факт вводится отдельно и план не двигает. Перевыполнение видно как факт>план, недовыполнение — как остаток «кол-во − факт» в верхней таблице.
Режимы проверок микроплана.
«Без / Прямой / От ШЦ». «От ШЦ» — не разворот цепочки: ШЦ планируется первым как якорь; поток физически остаётся РЦ→АЦ→ШЦ→У.

02.08.2026 — роли: кто что может править

Появились роли — в серверном режиме.
Раньше на сервере ограничение было одно: какие площадки (ОП) человек видит и правит. Теперь добавилось второе — какие разделы плана: «Справочники», «Заказы», «Макропланирование», «Микропланирование». Одно с другим перемножается: микропланировщик Бухары правит микроплан и только по Бухаре. У кого ролей нет — тот всё видит, но ничего не правит; это обычный режим для аналитика или руководителя.
Смотреть можно всё, что доступно по площадкам.
Роли ограничивают только правку. Читать разрешено всё в пределах своих ОП — иначе не посчиталась бы аналитика: она берёт микроплан, макроплан, заказы и справочники сразу. Чужую площадку человек по-прежнему не видит.
Что видно на экране.
В зелёной полосе серверного режима теперь пишется логин, роль и площадки на правку. Если раздел вам не открыт — рядом жёлтая пометка «Только просмотр», а поля и кнопки на вкладке погашены. Фильтры при этом работают: смотреть данные под разными срезами может и тот, кто их не правит.
Правка без права не «пропадает молча».
Если правка всё же ушла (например, права изменили в середине смены), приложение говорит об этом прямо и возвращает на экран данные сервера. Показанная, но не сохранённая строка опаснее прямого отказа: человек уйдёт с уверенностью, что план записан.
Журнал изменений — кнопка «Кто менял».
В серверном режиме видно, кто и когда правил: дата, логин, что за запись и что именно изменилось — «было 0 → стало 1234». Пересчёт месяца записывается одной строкой, а не тремя сотнями. Виден журнал только по вашим площадкам. Историю нельзя править — на то она и история.
Резервные копии базы — ежечасно.
Копия базы снимается каждый час, хранится двое суток почасовых плюс месяц ежедневных. Их состояние попадает в ежедневный отчёт: если копии перестанут сниматься, об этом придёт сообщение, а не выяснится при восстановлении.
Управление людьми — у администратора.
Кнопка «Пользователи» в полосе серверного режима: завести человека, выдать роли и площадки, сменить пароль, назначить другого администратора. Администратор — это признак учётной записи, а не роль в списке. Снять последнего администратора нельзя — иначе управлять правами станет некому.

31.07.2026 — шаг 0 подготовки к серверной версии

Единая метрика покрытия заказа — баг «план 0 при живом остатке» закрыт.
Раньше на вопрос «сколько по заказу уже покрыто» отвечали по-разному: подсказка ≤N (ЗАК) считала по чистому плану, ядро авто-плана и лимиты подзаказов — по max(факт, план). При перевыполнении ядро считало заказ выбранным и ставило план 0, хотя подсказка показывала живой остаток. При отставании наоборот: невыполненный план засчитывался как сделанный, и хвост заказа молча исчезал вместо удлинения графика. Введён единый хелпер orderCoveredBefore: прошлое считаем по факту, будущее — по плану; на него переведены все 7 мест. Метрику остатка теперь меняют в одной точке.
Смена заказа в строке микроплана пересчитывает изделие и норму.
Было условие «обновлять только пустую строку», из-за чего после исправления заказа план считался по норме прежнего изделия. Если артикул подходит и новому заказу (тот же ГП) — выбор пользователя сохраняется.
Проверки разделены на «стоп» и «предупреждение».
Раньше любое расхождение било модалкой «Всё равно сохранить?», и при опережении или отставании заполнение микроплана превращалось в череду подтверждений. Теперь: стоп (блокирует) — физика и порча данных: факт больше кол-ва заказа, выпуск больше суммы запусков, превышение лимита передела, нарушение последовательности дат; предупреждение (не блокирует) — расхождение планирования: план больше остатка заказа или больше плана предыдущего передела. План сохраняется молча, а расхождение видно жёлтым индикатором ≤N (ЗАК) ⚠ +M и янтарной полосой слева у ячейки плана; полный текст — во всплывающей подсказке.
Заведён каталог tests/ — автопроверки расчётов в Node.
cd tests && ./run.sh собирает харнесс, проверяет синтаксис и прогоняет тесты; можно натравить на любую копию из backups/. 65 проверок в пяти файлах. Это заготовка golden-master набора для будущего переноса расчётов в Python.
Экспорт/импорт: закрыта потеря данных при обмене между компьютерами.
Связи «заказ клиента ↔ заказ производства» и эффективность (ОП/цех/месяц) из загрузки макроплана не попадали в файл экспорта. Хуже: при загрузке чужого файла эти данные не сбрасывались, и на принимающей стороне оставались значения от предыдущего набора — связи указывали на несуществующие заказы. Обе коллекции теперь пишутся в файл и корректно заменяются при импорте; старые файлы читаются по-прежнему (связи восстанавливаются из контракта заказа).
Описан контракт данных — DATA_CONTRACT.md.
Что лежит в файле экспорта (21 ключ), что с ним делает импорт (22 миграции старых форматов) и о какие места споткнётся перенос в базу: ОП опознаются по имени, у заказа нет единого поля ОП, в файле нет версии формата. Первый артефакт фазы 0 подготовки к серверной версии.
Важно: перепланировщик НЕ возвращён.
Авто-план по-прежнему не двигает строки от факта — изменилось только то, как считается остаток. «Сжатие дат от факта» остаётся ручной кнопкой с подтверждением.

7. Подводные камни

  • Комплектные заказы. Остаток по переделу сейчас общий (кол-во − факт), не по узлам (куртка/брюки отдельно). Если понадобится раздельно для комплектов — доработка.
  • Заказы S.orders без поля op. Часть расчётов по заказу идёт по базовому маршруту; для ОП с переопределением комплектная проверка может быть неточной.
  • Firefox datalist. Поэтому поиск заказа сделан кастомным combobox (по подстроке во всех браузерах).
  • Кэш браузера. Сервер отдаёт no-cache — правки видны обычным F5. Если «залипло» — жёсткий Ctrl+Shift+R.
  • populateModules() в конце скрипта ссылается на пару неопределённых функций — в браузере тихая ошибка в самом конце, приложение работает (все функции уже объявлены). В Node-харнессе IIFE вырезают.
